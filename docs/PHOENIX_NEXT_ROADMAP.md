# PHOENIX-001 — 下一轮科研路线图

只保留三个方向。均使用本地 CPU 和已有/公开数据，不开启实时监控，不购买商业服务。

## 方向 1：恢复只读历史资产，完成证据契约与最小特征消融

**目标。** 回答 Q1、Q2 的前置数据问题和 Q4，优先验证最简模型是否真能超过 pair persistence。

**步骤。**

1. 获取既有 `medradar.sqlite` 和 `research.sqlite` 的只读副本，核对字节数、SHA-256、integrity_check；不重新抓取替代。
2. 用 `evidence_contract.py` 审计现有行，记录不能满足契约的字段，而非强制补齐虚构值。
3. 对 H2、H3、H8 做 leave-one-feature-out 和同窗口单特征试验，保持相同样本、滚动原点和训练参数。
4. 加入 HHI 与有效企业数，测试 H6；同时报告原始 ID 去重和派生血缘隔离。
5. 以 pair persistence 为主基线，预先设定最小有意义增量和误报预算。

**资源。** 约 1.4 GB 只读数据；本地 CPU 数小时，内存上限 4 GB；不需要 GPU。

**失败风险。** 原始库仍不可得、历史分类无法版本化、旧行无法补齐 alias/首次公开时间。任一情况都将对应假设保留为 blocked，而不是生成替代数据。

## 方向 2：建立试验→FDA 的成熟链接样本，检验 H5

**目标。** 回答 Q2：试验首次公开是否在监管持续性之外提供增量信息。

**步骤。**

1. 使用已有 ClinicalTrials.gov 和 S-029 产物，冻结 first-posted/update 时间、NCT ID、sponsor、所有权日期与证据链接。
2. 以 NCT ID 和派生关系为血缘键，映射到公司—赛道，并定义不重复的合格 FDA 里程碑。
3. 先报告五家公司覆盖率与选择偏差；样本不足时不扩展到全行业结论。
4. 比较 regulatory-only、pair persistence 与 regulatory+trial，报告 AP、P@K、R@K、误报、提前时间和公司留一稳定性。

**资源。** 本地 CPU 数小时；主要成本是实体审核和人工抽样，不是训练。

**失败风险。** 五家公司样本太小、sponsor 名称与母公司错位、试验和设备无法可靠对应、首次公开时间缺失。若独立事件不足，只发表描述性覆盖率，不做预测排名。

## 方向 3：冻结前瞻登记，积累真正的 category-4 验证

**目标。** 回答 Q1 和 Q5，检验历史持续性在真实公开时间下是否仍然存在。

**步骤。**

1. 在不启用本轮实时监控的前提下，预先冻结目标、模型、阈值和验证条件。
2. 后续只保存首次实际观察时间、来源快照和预测，不回改原预测。
3. 按 6、12、24 个月成熟窗口评估 pair persistence 与最简候选模型。
4. 同步测量 decision_date+14d 与真实首次公开时间的误差，做时间敏感性分析。

**资源。** 存储和本地 CPU 很小；主要成本是等待窗口成熟和持续数据质量管理。

**失败风险。** 正样本积累慢、采集间断、窗口过长。未成熟记录只能是 pending，不能进入成功率或校准报告。

## 投入顺序

先做方向 1。若原始库无法恢复，停止依赖行级重跑的方向，改做方向 2 的小样本链接审计；方向 3 的协议可以先冻结，但不把 pending 当结果。只有最简模型在真实时间约束下稳定超过 pair persistence，才值得投入复杂网络或 GNN。
