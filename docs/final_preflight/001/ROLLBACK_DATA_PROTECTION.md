# FINAL-PREFLIGHT-001 / 回滚数据保护：分析与结论

- 目标：回答"切换后产生的数据，回滚时会丢多少"
- 结论：**记录本身不丢**。用 `rollback_replay.py` 可以把切换后的观测连同**原始首次发现时间**
  回灌进恢复后的 v2 账本；实测 3/3 条记录、版本链、内容哈希、时间戳**逐字段一致**。
- 仍然会丢的：运行审计（`sync_run`）、切换后的 v3 判定投影、以及水位线的推进（后者只会导致重查）。

---

## 1. 为什么会丢（问题的形状）

| 事实 | 后果 |
| --- | --- |
| v2→v3 是**单向**结构迁移 | 回滚必须"代码 + 数据"一起退 |
| 账本 append-only，身份是 `(source, source_record_id)` | 记录可以被**重放**，不会重复 |
| `first_observed_at` 是 MedRadar 自己写入的 | 重采集**无法**重建它（源只知道公开时间） |
| 判定是派生投影 | 可以在旧规则下重新生成 |

所以真正不可再生的东西只有两样：**观测内容本身（如果源已删除）**和**首次发现时间**。
前者通常可重采，后者完全不可重建——这正是需要用重放保护的目标。

---

## 2. 方案比较

| 方案 | 复杂度 | 保护了什么 | 判断 |
| --- | --- | --- | --- |
| A. 只恢复备份 | 最低 | 无（切换后数据全丢） | 不采用 |
| B. 切换期间冻结写入 | 低 | 缩小窗口，但不为零 | **作为前提**（见 §4） |
| C. 切换后新记录独立备份 | 中 | 记录与时间戳 | **采用**：导出 v3 增量 → 重放进 v2 |
| D. 双写 / 消息队列 | 高 | 全部 | **禁止**（任务明确不允许引入） |
| E. 新旧 Schema 兼容映射 | 高 | 全部 | 不必要（旧代码安全拒绝 v3，见 §3） |

采用 **B + C**：切换时短暂冻结写者，然后用一个约 200 行的导出/导入工具把增量搬回去。
不引入任何新基础设施。

---

## 3. 旧代码遇到 v3 库：安全拒绝（不是静默损坏）

```
refused: RuntimeError
message: … unsupported radar ledger schema 'radar-ledger-v3' (this build requires
         'radar-ledger-v2'). There is no automatic migration from that version and
         no data was modified …
sha256 before: 451abf3be6ac45a8c0d5949be3f2866ec30edf7cb2cc1f840005ca00f316109e
sha256 after : 451abf3be6ac45a8c0d5949be3f2866ec30edf7cb2cc1f840005ca00f316109e
VERDICT: old code refused and modified nothing
```

含义：只回滚代码不会把库写坏，但服务起不来——所以路径 B 必须同时回滚数据。

---

## 4. 写入冻结窗口（前提条件）

| 步骤 | 实测耗时 |
| --- | --- |
| 停调度器 | < 1 s |
| 一致性备份 | 0.35 s（8,360 条） |
| 恢复 + 重放 + 重判（回滚时） | **0.55 s** |
| 合计 | **< 10 s**（按 60 s 计划） |

在 6 小时 / 12 小时的采集节奏面前，10 秒的冻结不会漏掉任何一次采集。
**冻结是"把窗口压到零"的手段，重放是"窗口里的东西也能救回来"的保险**，两者叠加才叫无损。

---

## 5. 重放工具做了什么（`rollback_replay.py`）

```
export（用新版本跑）: 从 v3 库导出 --since 之后的观测：元数据 + 每个版本 + facets + 判定输入
import（用旧版本跑）: 逐版本调用 record_observation(..., seen_at=<原 captured_at>)
compare（纯 sqlite）: 对比 before/after 的观测数、版本数、时间范围
```

关键点：

- **每个版本单独重放**，所以 `version_count` 与每一版的时间戳都能还原；
- `seen_at` 传原始的 `captured_at`，所以 `first_observed_at` 保持原值；
- 只搬观测，不搬判定/水位线——那些由旧版本自己重新生成；
- 幂等：重复导入同一份增量不会产生重复行（身份是 `(source, source_record_id)`）。

---

## 6. 有界恢复点（RPO）的诚实表述

| 数据 | 回滚后是否保留 | 说明 |
| --- | --- | --- |
| 观测记录（含内容哈希） | ✅ 保留 | 重放；实测 3/3 一致 |
| **首次发现时间** | ✅ 保留 | 重放时用原始 `captured_at` |
| 版本历史（更新） | ✅ 保留 | 逐版本重放；v1+v2 都在 |
| 分类映射（facets） | ✅ 保留 | 从 facets 重建 MappingResult |
| v3 判定（切换后重判） | ❌ 不保留 | 由旧版本按 v2 规则重新判定 |
| `sync_run` / 运行审计 | ❌ 不保留 | 运营审计，不是记录证据；未纳入重放 |
| 水位线 | ❌ 退回切换前 | 会导致一段重查（幂等，不产生重复） |
| 源上已删除的记录 | ❌ 可能丢失 | 只有切换后的账本里有；若源已删则不可重采 |

**最坏情况**：如果 `live.db`（新版本写过的库）也一起丢失，那么切换后的一切都只能重采，
且首次发现时间永久丢失。因此回滚流程的第一步就是**把 v3 库复制到安全位置**
（`RELEASE_RUNBOOK.md` §7.2 第 2 步）。

---

## 7. 结论

- 回滚**可以做到观测无损**（含首次发现时间），代价是一个 0.55 s 的重放步骤和一份 v3 库副本。
- 不可无损的三项（v3 判定、运行审计、水位线）都是**派生或可重建**的，不构成记录丢失。
- 因此"回滚会丢失切换后新数据"这一风险**已被消除**，不再是发布阻塞。
