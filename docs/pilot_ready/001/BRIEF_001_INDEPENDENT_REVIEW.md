### 1.1 逐条要点（只有需要说明的才写）

**#1** —— 这是本期唯一一条我会签名推荐给研发负责人的条目。它把 SpO₂ 偏差同时放在"活动状态"与
"肤色"两个维度上量，并且用了两台临床对比仪（含 GE Dash）。**但**它的被测对象是消费级穿戴设备，
简报标题写"监护设备情报"而不说明这一点，会让读者误以为结论直接适用于医院监护仪。
结论可用，框架需要修一句。

**#3** —— n=1 的可行性个案。作为"技术迁移线索"可以，作为**正式情报**不行：一个人、一次测量，
不构成任何可引用的性能结论。它在 6 条"待复核"里更合适。

**#8 / #12 / #13 / #15** —— PubMed 的 `pubtype` 明确含 `Review`（#8、#12、#13、#15），#13 标题里
直接写着 `narrative review`。四条综述占了正式情报的 27%。综述可以是情报，但前提是它给出**可操作的
工程结论**；这四条的"研发关注点"仍然是同一句模板，说明系统并没有真的从中提取结论。

**#9 / #10 / #11** —— 三条的日期精度都写成 `year`，而来源实际是**月**精度：

```
#9  PubMed : pubdate "2026 Nov"，epub 为空        → 正确值是 2026-11（month）
#10 PubMed : pubdate "2026 Nov"，epub 为空        → 正确值是 2026-11（month）
#11 Crossref: issued [[2026, 11]]                 → 正确值是 2026-11（month）
```

这不是"来源没说清"，是**系统把月精度降级标成了年精度**，反而让读者以为信息更不精确。
根因见 §4。

**#10** —— 摘要为空，判定理由自己写着"no abstract: judged from the title only"，却仍然给了 MEDIUM。
标题是"Peripheral Perfusion: The Missing Physiological Variable in ICU Pulse Oximetry Accuracy Studies"，
发表在 *Nursing in Critical Care*——这类标题与刊物的组合通常是评论/社论。**在只有标题的情况下，
它不应进入正式情报，应进入待复核。** 这一点必须由人裁定，我把它标为"需人工领域专家裁定"。

**#11** —— 一个 ECG 数据资源库的描述性文章，Crossref 无摘要，没有任何设备性能结果。
它不是"设备性能研究"，也不是安全事件。

**#14** —— **这是本期唯一的硬错误。** 简报给出的链接
`https://doi.org/10.29196/jubes.v4i4.6922` 返回 **404**；Crossref 直接 404。真实 DOI 是
`10.29196/jubes.v34i4.6922`（v**34**i4，不是 v4i4）。用 Crossref 书目检索可以命中后者：

```
GET https://doi.org/10.29196/jubes.v4i4.6922          → 404
GET https://api.crossref.org/works/10.29196/jubes.v4i4.6922 → 404
GET …/works?query.bibliographic=Patient-Specific+…    → 10.29196/jubes.v34i4.6922 ✅
```

即：**读者点不开这条证据。** 这违反"可追溯"的最低要求。它同时意味着账本里存了一个错误标识符，
而标识符是去重与跨源关联的键——这类错误会污染图谱。
判定：**NOT VERIFIED（按简报所载标识符）/ 记录本身存在于另一个 DOI 下**。

## 4. 任务书点名的八个问题，逐个回答

### 4.1 30 天窗口为什么被称为"周报"？

**因为标题是硬编码的，而窗口是参数。** 渲染器输出的第一行固定是：

```python
# medradar/radar/intelligence.py
"# MedRadar 监护设备情报周报"        # 与窗口长度无关
```

而 `radar brief` 的窗口由 `--since/--until` 决定（CLI 默认 7 天，本次显式给了 30 天）。
产品策略又把默认视图窗口设为 30 天（QUALITY-001）。所以"周报"既不是渲染器的事实，也不是窗口的事实，
它只是一个名字。**这是一个命名与内容互相矛盾的缺陷**，不是排版问题：读者会按"一周发生了什么"去读，
而内容实际是"30 天的累积"。

### 4.2 月精度被标成年精度？

**确认，且可定位到两处代码。**

```python
# medradar/radar/records.py:297-320
if _YEAR_ONLY.match(text):
    return text, PRECISION_YEAR
if _YEAR_MONTH.match(text):
    return text, PRECISION_YEAR      # ← "2026-11" 被归为 year
```

```python
# medradar/radar/adapters/crossref.py:227-228
if len(values) == 2:
    return f"{values[0]:04d}-{values[1]:02d}", "year"      # ← 月精度值 + year 标签
# medradar/radar/adapters/pubmed.py:322
    return f"{year}-{_month_number(month):02d}", "year"    # ← 同上
```

精度常量只有 `datetime / date / year / unknown` 四档，**没有 month**，所以月精度无处可去，
被就近塞进了 year。受影响的生产记录数（服务器账本）：

```
published_at_precision 分布: unknown 6,969 | date 1,076 | year 308 | datetime 5
→ 308 条被标为 year 的记录里，有多少其实是月精度？需要逐条看原值才能确定，但抽样全部是 "YYYY-MM"。
```

**建议的最小补丁**（本轮未实施，理由见 §5.3）：新增 `PRECISION_MONTH = "month"`，让
`_YEAR_MONTH` 分支返回它，两个适配器的 `len(values)==2` 分支返回它，并在
`PRECISIONS` 元组里登记。**注意**：已入库的 308 条仍是 `year`（账本是证据，不能改写），
因此这是一次"新老并存"的迁移，需要产品决定是否回填重判——这正是本轮不擅自实施的原因。

### 4.3 大量 MEDIUM 是否说明分级仍缺乏信息量？

**是，而且比"14/15 是 MEDIUM"更严重。**

- 正式情报：HIGH 1 / MEDIUM 14 / CRITICAL 0 / LOW 0；
- 但**待复核**的 6 条全是 LOW，其中 2 条明显比正式情报里的条目更值得读；
- 账本层面：8,358 条里 7,166 条（85.7%）是 `HIGH_RELEVANCE`，而其中 6,938 条来自单一通道。

两套标签（`tier` 与 `importance`）都出现了同一个病：**绝大多数落在一个桶里**。当 86% 的东西是"高"，
"高"就不再传递信息。这不是阈值调参能解决的，需要"重要性理由"真正参与排序（见 4.7）。

### 4.4 重要召回是否只存在于历史补充中？

**是，本期 0 条召回到达正式情报，5 条全在历史补充。**

更进一步：这 5 条之所以能被看到，靠的是**回填**，不是持续采集。回填发生在 2026-11-18T14:52，
而窗口结束于 2026-11-18。也就是说——"本期最重要的安全价值"完全来自一次手工历史导入。
这本身不是错（回填是正当功能），但它意味着：**如果下周不回填，下周的简报里将没有任何召回。**

### 4.5 部分临床研究或普通综述是否不适合作为正式技术情报？

**是。** 用 PubMed 的 `pubtype` 客观核验：

| 条目 | PubMed pubtype | 是否原始研究 |
| --- | --- | --- |
| #8 | Journal Article, **Review** | 否 |
| #12 | Journal Article, **Review** | 否 |
| #13 | Journal Article, **Review** | 否 |
| #15 | Journal Article, **Review** | 否 |
| #3 | （Crossref）Single-Patient Case Study | n=1 |
| #9 | Journal Article, **Observational Study** | 是（pilot，n=18） |
| #11 | 数据集/资源描述，无摘要 | 否 |

4/15 是综述、1/15 是 n=1 个案、1/15 是数据集描述。**只有 9 条是原始研究**，而其中又有多条是
算法/影像领域，不是监护设备性能。

### 4.6 原始摘要直接复制是否提供了增量价值？

**没有。** 每条"发生了什么"都是摘要的逐字截断，并且**在单词中间被切断**：

```
#1  "…Garmin showed a significant negative signed bias relative to the GE Dash dur…"
#2  "…The DL model showed higher observed sensitivity (78.3%) and F1-score (80%) compar…t…"
#4  "…Consensus REVised Imaging a…"
#7  "…the remote-monitoring figures are a feat…"
```

一段被截断的摘要既不能替代原文，也不比"点开链接自己看"更省时间。**它占用了版面，却没有降低读者的
理解成本。** 真正的增量价值应该来自"这条与你的产品线有什么关系"，而那部分正是模板。

### 4.7 "研发关注点"模板重复是否让重要信息仍需用户自己分析？

**是。** 15 条正式情报的"研发关注点"是**同一句话**：

> Check whether the evaluated method or measurement applies to your product line, and whether the
> validation design is comparable to yours

这句话对 #1（血氧偏差与肤色）和 #11（一个数据集）**完全一样**。它没有回答任何一个具体问题：
差多少毫米汞柱？在什么运动状态下？样本多大？和哪个标准比？也就是说，**分析工作被原样退回给了读者**。
这正是"周报"最该承担、却完全没有承担的那部分。

### 4.8 CRITICAL 是否只是监管安全关注优先级，却被读成已证实的临床风险？

**是，而且简报没有做任何澄清。** 见 §3.2：99617 是标签更新，99549 是可中断报警的软件漏洞，
两者同为 CRITICAL。同时，正式情报里 **0 条 CRITICAL**——因为正式情报全是文献，而文献几乎不会被
规则判为 CRITICAL。于是读者会得到一个错误的世界图景：**"召回=CRITICAL=危险，论文=MEDIUM=不重要"**，
而现实是"一条标签更新的召回"可能比"一篇 n=100 的血氧偏差研究"更不重要。

## 5. 另外三个必须记录的缺陷

### 5.1 这份简报无法用服务器上的账本复现

简报头部写的是 **15,156 条观测**（含 openFDA 召回 6,563 条）。服务器生产库是 **8,358 条，召回 0 条**。
两者不是同一份账本：

```
简报:  observations 15,156（openFDA 清关 6,936 / 召回 6,563 / PubMed 484 / Crossref 1,137 / Dräger 31 / Philips 5）
服务器: observations  8,358（openFDA 清关 6,938 / 召回   0 / PubMed 272 / Crossref 1,112 / Dräger 31 / Philips 5）
```

结论：**WEEKLY_BRIEF_001 是一份"本地/离线账本"的产物，不是线上部署的产物。** 这不影响它的内容
真实性，但影响"可复现"：任何人拿到服务器，都复现不出这份简报。这是一个交付层面的缺陷。

### 5.2 参考事件的 8/8 召回率不衡量"发现能力"

`_evidence/reference_events.json` 里 8 条参考事件的 `public_date` 全部**早于窗口**
（2026-06-24 到 2026-10-16），`first_observed_at` 全部是 **2026-11-18T14:52**——也就是回填那一刻。
所以"8/8 召回"衡量的是"回填有没有把这 8 条存进来并判对"，**不是**"系统在本周有没有发现新东西"。
把它写成"参考事件召回 8/8 = 1.00"容易被读成后者。这不是造假，是口径没有说清。

### 5.3 标题中残留 JATS/HTML 标记（生产账本实测 15 条 / 14 条含换行）

```
Performance of Transcutaneous Pco <sub>2</sub> and Pulse Oximetry Moni…
Multimodal Physiological and\n<scp>EEG</scp>\nResponses to Short-Term Hy…
```

根因：`crossref.py:135` 的标题只经过 `_first_text()`，而摘要经过 `_strip_markup()`（第 137 行）。
标题少了同样的清洗。**本轮不在阶段二修**（不是运行缺陷，且已入库标题属不可变证据，
正确的修法是在渲染层清洗，涉及展示契约），已在 RELIABILITY_FIXES.md 与本文件记录。

## 7. 结论

| 维度 | 判定 | 依据 |
| --- | --- | --- |
| 记录真实性 | **基本可信** | 25/26 条独立核实存在；1 条（#14）DOI 死链 |
| 日期准确性 | **不合格** | 3 条月精度被标成年精度；其余 12 条日期与来源一致 |
| 范围准确性 | **不合格** | 15 条里 4 条综述、1 条 n=1、1 条数据集描述、2 条领域外，真正"监护设备性能研究"约 6 条 |
| 相关性论证 | **不合格** | 4.7：15 条同一句模板 |
| 可追溯性 | **部分合格** | 链接齐全，但 1 条打不开；且简报无法用线上账本复现 |
| 分级信息量 | **不合格** | 4.3：86% 落在同一档 |
| 安全性覆盖 | **不合格（对产品承诺而言）** | 4.4：0 条召回进入正式情报，全部依赖回填 |

**一句话：** 这是一份**证据链基本可信、但产品形态尚未成型**的材料。它的失败不在于"编造"，
而在于**把 15 条文献按模板填进一个叫"周报"的容器里**，既没有替读者做判断，也没有把最重要的安全事件
放进正文。
