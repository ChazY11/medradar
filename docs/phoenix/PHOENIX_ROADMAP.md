# PHOENIX-001 — 下一轮路线图

> 原则：**只推荐被本轮数据指出来的方向**，不推荐"功能更多"的方向。
> 每个方向都给出：为什么现在做、要什么、成本、**失败长什么样**（可证伪）。
> 约束不变：不上云、不租 GPU、不买数据、不新增依赖、不自动合并。

---

## 排优先级的三条依据

1. **数据限制优于方法改进**：本轮证明复杂方法只带来 <0.013 AP。继续调模型是低回报。
2. **唯一能升级证据等级的路径是采集**：没有 as-of 记录，永远停在"受约束回测"。
3. **已被数据指出但尚未利用的机会优先**：H7 已显示"小赛道用固定阈值、大赛道用 CUSUM/PELT"更好（.652/.859 vs .560/.532），这是白送的机会。

---

# R1（最高优先）：建立真正的 point-in-time 采集层

**为什么现在做**
本轮最硬的发现是：`available_at == event_date`，且整库只有两天的 `fetched_at`。这意味着**MedRadar 目前无法产生第 4 类证据**——无论方法多好。这是唯一一条**方法无法绕过**的限制。

**做什么**
- 不重建现有库。**新增一张 append-only 的 as-of 事实表**（如 `event_snapshots`），只记录"我们在某时刻看到的某事件"。
- 每日/每周对 openFDA、ClinicalTrials.gov、SEC EDGAR 做**增量拉取**，每次写入 `(event_id, observed_at, field_values_hash)`。**不覆盖历史**。
- 唯一必须保证的不变式：**任何一条历史记录一旦写入，永不更新**（只追加新版本）。
- 从第一天起就登记**前瞻预测**：每次给出预测时，把 `(预测时间, 单元, 目标窗口, 预测值)` 写进 `prospective_registry` 表 —— 这正是仓库里已有 `FORECAST_REGISTRY` 概念的自然延伸。

**需要什么**
- 现有 `medradar` 采集器 + 一个 append-only 表 + 一个调度（本机计划任务即可）。
- 磁盘：按现在 375k 事件的体量，增量快照每年 < 5 GB。
- **零新增依赖**（标准库 sqlite3 足够）。

**成本**
- 开发 **3–5 天**；运行成本 **≈ 0**（本机，无云）；运维负担：每日检查一次采集是否成功。
- 首次产生可用前瞻证据：**6 个月后**（4 季前瞻窗口 + 缓冲）。

**失败长什么样（可证伪）**
- 若 6 个月后 `prospective_registry` 里的预测表现与回测估计**显著不一致**（例如 AP 大幅下降），则说明现有结论存在系统性回测乐观偏差 → **必须下调所有历史结论的可信度**。这是一个有价值的负面结果，不是失败。
- 若采集频率跟不上（某源发布延迟 > 90 天），则 L090 假设失效 → 报告实际延迟分布。

**风险**
- 中。主要风险是"运行半年但样本太少（正样本不足）导致无法判定"。缓解：同时登记**负样本预测**，用发生率与校准而非仅 AP 来评估。

# R2：变化点检测的分层策略（几乎零成本，已有全部数据）

**为什么现在做**
H7 已给出明确的分层证据，但我们**还没利用它**：
- 小赛道：固定阈值 .652 vs CUSUM .560 / PELT .533
- 大赛道：CUSUM .859 / PELT .871 vs 固定阈值 .532

**做什么**
- 在已有的 24,000 条半合成序列上，加一个**分层臂**：按赛道季度事件量中位数切换检测器。
- 预注册判定：分层策略在匹配误报预算下的检出率，比**任何单一检测器**高 ≥5 pp。
- 若成立，把它做成一个独立的小模块（不接入生产，先做实验模块）。

**需要什么**
- 已有的 `changepoint_bench.py` 与全部中间结果。**零新增数据、零新增依赖。**

**成本**
- **0.5–1 天**。纯本地计算。

**失败长什么样**
- 若分层策略不优于最优单一检测器（+<5 pp），则**放弃分层**，直接采用 CUSUM/PELT。这也是有价值的结论（说明切换成本不值得）。

**风险**
- **极低**。这是本轮性价比最高的一个方向。

# R3：实体归因的下游影响评估（决定 RAEA 能否晋级）

**为什么现在做**
RAEA 已把 510(k) 企业覆盖率从 13.36% 提到 15.68%（+8,914 条归属），**但我们没有度量这会不会改变既有结论**。在没有度量之前把它并入生产，就是"看起来更好就合入"，违反项目原则。

**做什么**
1. 在 RAEA **之前**与**之后**各跑一次 `T-CELL` 面板，比较 H1/H4/H8 的 AP 与聚类 bootstrap CI。
2. 随机抽 **100 条**新增归属做人工独立复核，报告复核精度与 Wilson 95% CI。**低于 0.95 不得晋级。**
3. 跑 L6 检查：新增归属是否导致同一 `product_code`+企业+日期被计两次。
4. 与现有 `product_entity_map.sqlite` 交叉验证一致性。
5. 结论若为"影响不可分辨"，**明确写出来**——不要为了给模块找价值而夸大。

**需要什么**
- 本轮的 RAEA 模块与面板构建脚本（都已存在）。
- 人工复核 100 条：约 2 小时。

**成本**
- **1–2 天**（其中人工复核 2 小时）。

**失败长什么样**
- 若复核精度 < 0.95 → RAEA 不晋级，改为"仅作数据质量报告"。
- 若 AP 的 CI 前后重叠 → 结论"影响不可分辨"，**不晋级**，但保留模块作为数据卫生工具。

**风险**
- 低。最大的风险是**诱惑**：新增 8,914 条归属看起来像进步，容易让人跳过验证。本文件的判定规则就是为了防这个。

## 明确**不推荐**的方向（以及为什么）

| 不推荐 | 理由（本轮证据） |
|---|---|
| 引入图神经网络 / 更复杂模型 | H10：图+梯度提升只带来 **+0.0123** AP，且低于预注册阈值 0.03。继续加大模型复杂度是低回报 |
| 多数据源融合 | H9：融合/最强单源 = **0.966**，**融合更差** |
| 用 8-K 做领先信号 | `track_id` 覆盖率 **0/20,976**。这是**数据工程**问题，应先修 schema 再谈信号 |
| 采购外部专利/文献数据 | 本轮已确认这些方法依赖 MedRadar 没有的语料；采购违反"不增加云/采购成本"约束 |
| 集成 REA 作为默认依赖 | 207 工具、未修复的 `zod` CVE、未签名原生扩展。按需使用即可（ADAPT） |
| 重跑 S-028 并声称"复现" | 桥接实验已证明**风险集口径不同**，发生率 6.76% vs 1.02%。只能报"未复现" |
| 把 RAEA 直接合入生产 | 下游影响未度量，复核精度未测。必须先过 R3 |

## 建议的执行顺序与总成本

| 顺序 | 方向 | 工期 | 运行成本 | 依赖 |
|---|---|---:|---|---|
| 1 | **R2 变化点分层** | 0.5–1 天 | ≈0 | 无（数据已就绪） |
| 2 | **R3 实体归因影响评估** | 1–2 天 | ≈0 | 无（模块已就绪） |
| 3 | **R1 point-in-time 采集层** | 3–5 天开发 + 6 个月运行 | ≈0 | 需长期运维承诺 |

**总计**：约 **1 周开发**（R1+R2+R3），此后 R1 需要 6 个月的**无人值守运行**（每日一个计划任务）。

## 下一轮的验收门槛（预先写定）

1. R2：分层策略 Δ 检出率 ≥ +5 pp，且配对 bootstrap p<0.05。否则放弃分层。
2. R3：人工复核精度 ≥ 0.95（Wilson 下界），否则 RAEA 不晋级。
3. R1：`prospective_registry` 至少积累 **100 条**预测且目标窗口已到期，才能做第一次前瞻评估。少于 100 条时**不得**下任何前瞻结论。
4. 全部三条：**数据库 SHA-256 保持 `445807CA…97002C92` 不变**（不得为做实验而改写历史库）。R1 必须用**新表**，不得原地修改。

## 最后一句

> 本轮的结论不是"MedRadar 需要更多功能"，而是**"它需要一个诚实的时钟"**。
> 在补上 point-in-time 之前，任何对未来的说法都只能叫回测。
