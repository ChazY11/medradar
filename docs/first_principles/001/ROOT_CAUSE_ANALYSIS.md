# FIRST PRINCIPLES-001 / 第四阶段：真正的系统瓶颈

- 输入：`USER_PROBLEM.md`、`INTELLIGENCE_STANDARD.md`、`REFERENCE_EVENTS.md`、`INDEPENDENT_EVALUATION.md`
- 目标：把"代码哪里不好"换成"哪一步让用户损失了什么"，并据此排序。
- 排序公式：**对核心用户价值的影响 × 发生可能性 × 解决收益 ÷ 解决成本与风险**

## 0. 一张图说清瓶颈在哪

```
来源 ──采集──> 账本 ──准入──> 情报池 ──展示──> 用户
  │              │             │            │
  │ 缺召回        │ 95.6% 是     │ importance │ QA-002：500/404、
  │ 缺 NMPA      │ 24 个月前的  │ 常量       │ 能力语义错误
  │ 缺竞品产品     │ 档案         │            │
  │ 检索式太窄     │              │            │
  └─ R1/R2/R3 ────┴─ R3/R4 ─────┴── R3 ──────┴── R8
```

一句话：**瓶颈不在"判断得准不准"，而在"该采的没采、采到的分不出新旧、分出来的排不出优先级"。**

## 1. 根因排序（每条都给出真实业务损失）

### R1（致命）监管安全事件通道根本不存在

- **证据**：openFDA 的 `/device/recall.json` 本轮实测可用；13 个已配置监护产品码下共 **734 条召回记录**，
  其中 **2026 年 42 行 = 19 个召回事件**，涉及 Philips / GE / Mindray / Nihon Kohden / Spacelabs / Criticare / Midmark / Masimo。
  账本中召回记录 **0 条**；`radar/adapters/` 下无召回适配器；
  `config/radar/sources.json` 里 `read_path` 甚至写了 `/device/recall.json`，但没有实现。
- **业务损失**：用户最需要、最不可替代、最愿意付费的一类信息（"已上市监护设备的失效与召回"）
  覆盖率是 **0%**。2026-07-20 GE Portrait 软件"可能导致失去监护"、2026-07-31 Philips PIC iX 冻结、
  2026-07-01 Philips 心电工作站数据错误——任何一条，对做中央站/监护仪的团队都是必须当天知道的。
- **发生在链路哪一步**：S1（来源存在，适配器未采集）。
- **修复成本**：低—中。一个适配器 + 产品码映射 + 幂等/水位线测试。
- **为什么不是算法问题**：引擎已经能正确识别 recall 类记录（D12 已确认），缺的只是"数据没进来"。

### R2（致命）采集范围由 7 条固定检索式定义，而不是由领域定义

- **证据**：PubMed 适配器 7 条检索式，全部强制 `AND ("intensive care" OR "ICU" OR "patient monitor")`，
  每条最多 300 条。本轮用 6 条更宽的检索式在 48 天窗口取到 454 条候选，抽样 400 条，
  库中只有 114 条（**28.5%**），286 条从未被请求；其中约 25–30 条属 DIRECT/TRANSFER，
  包括 2026-11-17 发表的 ICU 血压估计（PMID 43044098）——就在账本复制前一天。
- **业务损失**：用户无法知道"系统没找到"与"世界上没有"的区别。这是**沉默的漏检**：
  系统不会报错，用户会以为覆盖率是完整的。技术方向的早期信号正是靠这一类"措辞不同"的论文。
- **发生在链路哪一步**：S2（已采集，但检索范围未覆盖）。
- **修复成本**：中。检索式是可配置的（`adapters/pubmed.py: QUERIES`），扩大范围会带来噪声；
  所以正确做法是"宽采集 + 严格准入"（REF-004 已经删除了入库前过滤，这条前提现在成立了）。
- **风险**：扩大采集会增加入库量，而当前 importance 是常量（R3），需要同时解决 R3，否则噪声会直接进简报。

### R3（高）"归档"与"新情报"没有分离，且重要性维度是常量

- **证据**：情报池 7,360 条 FEED 中 **7,039 条（95.6%）早于 24 个月**，只有 178 条在 12 个月内；
  `importance` 在 FEED 内分布为 **HIGH 3 / MEDIUM 7,357 / LOW 0**；
  8,593 条观测中 **8,588 条是 INITIAL_DISCOVERY**（首次导入），仅 5 条增量。
  默认 30 天简报的 21 条全部 importance=MEDIUM。
- **业务损失**：
  1. 用户在"技术主题/企业"视图里看到的是半个世纪的清关档案，而不是"最近发生了什么"；
  2. 21 条简报没有优先级，用户必须自己重排；
  3. 任何"变化"视图（技术树的 what changed）都会显示 17,686 条建库断言（QA-002 实测），
     等于把导入噪声当成技术突变。
- **发生在链路哪一步**：S5（已准入但未按"变化"呈现）+ 判断层的 importance 维度失效。
- **修复成本**：低（策略）—中（规则）。不需要新架构：一个"新鲜度闸门 + 三档重要性规则"即可，
  但**需要一个产品决定**：档案是否应该出现在默认视图（本轮判断：不应该）。

### R4（高，本轮已修）水位线不可用，Crossref 增量实际在扫 2018 年以来的全部数据

- **证据**：真实账本 `source_state.crossref.watermark = "2027-02"`。
  `CrossrefAdapter._since()` 对 `normalize_moment("2027-02")` 得到 `"2027-02"`，
  `date.fromisoformat` 抛 `ValueError`，于是回退到 `EARLIEST = "2018-01-01"`。
  本轮实测：修复前请求窗口是 `from-created-date:2018-01-01`，修复后是 `2026-11-16`。
  同时 `_max_moment([2027-02, today])` 永远保留 2027-02，所以**永远不会自愈**。
- **业务损失**：Crossref 的 6 条检索式每次都在近 9 年的语料上做相关性排序取前 3 页（300 条），
  新沉积的论文与 2018 年的高相关论文竞争同一个名额，**新内容被系统性挤出**；
  而运行状态一直显示 OK，没有任何告警。这是"系统看起来在跑、实际在空转"的典型。
- **发生在链路哪一步**：S4 之前（采集窗口本身错误）。
- **修复**：已实施（见第 3 节），最小改动，可回滚。

### R5（高）企业情报通道采集的是错误的主体

- **证据**：Philips 5 条全部是集团新闻室内容（AGM 提名、Sonicare 牙科、HyperVue/UniGuide 影像、
  EXIT-CVD 联盟），**0 条与监护相关**；Dräger 31 条来自 **Dräger Safety（工业安全）** 的 sitemap：
  海滩清理、矿山安全、清洁能源、气体检测、INARA、"Be creative"，只有 2 条勉强相关；
  GE HealthCare 的 robots.txt 返回 403，来源被正确标为 BLOCKED（0 条）。
- **业务损失**："企业科技树"这一核心卖点没有输入。36 条标题无法支撑任何产品能力判断，
  而 QA-002 已经把"把 TOPIC_RELATED 显示成 capability"判为语义错误——现在连可显示的内容都很少。
- **发生在链路哪一步**：S0/S1（来源选择错误）。
- **修复成本**：低（换 sitemap / 换板块），但要先回答"是否要做企业情报"（产品定义问题）。

### R6（中）同一件作品在存储层会重复

- **证据**：合成实验（隔离库）中，同一 DOI 以两个不同的 `source_record_id` 到达 → 产生 **2 条 observation**，
  两条都是 NEW。存储身份是 `(source, source_record_id)`，不是"作品"。
  REF-004 的 `work_key` 只在展示层归并，且其回归测试只覆盖了"同标题不同 DOI 不应合并"这一个方向。
- **业务损失**：计数虚高（"有多少条证据"变成"有多少个来源行"）；同一事件可能在简报里出现两次；
  以计数为基础的对比视图（企业 A vs B）会被重复扭曲。
- **发生在链路哪一步**：账本（入库身份）。
- **修复成本**：中（需要 works 表或 DOI/PMID 唯一约束 + 迁移），**本轮不做**：
  因为当前数据里真实的同 DOI 跨源重复量未知，需要先测量再决定。

### R7（中）分类器在 TRANSFER / MEDICAL_UNRELATED / NON_MEDICAL 上不可靠

- **证据**：独立 120 条样本一致率 DIRECT 0.84、CLINICAL 0.84，但 **TRANSFER 0.17（1/6）、
  MEDICAL_UNRELATED 0.30（6/20）、NON_MEDICAL 0.36（4/11）**；
  3 条高价值假阴性（NIBP 系统综述、隐匿性低氧、ECG 算法）都在真实数据里。
- **业务损失**：真实损失集中在假阴性（漏掉该看的）+ 解释错误（"为什么排除"说错）。
  对用户而言，后者比前者更伤信任，因为用户会用这个解释去判断系统是否可信。
- **发生在链路哪一步**：准入判断。
- **修复成本**：中—高，且**边际收益递减**。REF-004 已经在这个方向上投入了一整轮（876 行、
  703 个 CC>10 的函数），本轮不建议继续加规则；建议改为"可解释的候选 + 人工复核队列"。

### R8（中，本轮未复验）UI 层的确定性缺陷

- **证据**：QA-002（2026-11-17 公网实测，结论 FAIL）：公开时间回溯 500、证据节点 404、
  把 TOPIC_RELATED 显示为 capability、移动冷启动 8.9–16.6 秒、截断后无分页。
- **本轮状态**：**未复验**（无部署访问）。REF-004 声称修复了其中一部分（时间精度、分页、维度芯片），
  但 QA-002 的原始证据目录（`evidence/*.json`）不在本机，无法核对。
- **业务损失**：用户点开证据看到 500/404，等价于"没有证据"。
- **修复成本**：低（逐条），但需要一次真实浏览器复验。

### R9（结构性）交付形态：九层未合并草稿 + 三条并行车道 + 57k 行文档

- **证据**：`main` = 86311b1（PR #41 合并），**不包含产品与雷达**；PR #46–#54 是严格线性堆叠的
  9 个 open 草稿，全部未合并；`refoundation/004` 是本地分支（不在 origin），在 #54 之上再加 9 个提交，
  相对 main 变更 662 个文件、+187,080/−1,037 行。
  代码 154,996 行 Python + 13,181 行 TS/TSX；同时有 **57,416 行 Markdown（564 个文件）**。
- **业务损失**：任何修复都必须落在栈顶，评审者要一次看 18 万行；产品无法被外部用户使用（不在 main）；
  文档量已经超过代码量的 1/3，但产品 30 天只输出 21 条。
- **这是"真实业务没有要求"的复杂度**：57k 行文档不产生情报，只产生"看起来在进步"。

### R10（低）监管产品码映射噪声

- **证据**：`ARISTO MEDICAL MODEL 2101 PATIENT MONITOR` 的 product_code 是 DQA（Oximeter）。
  患者监护仪被映射为血氧计，说明"产品码 → 主题"的映射没有做一致性检查。
- **业务损失**：主题计数轻微失真，不影响简报。
- **修复成本**：低，但优先级低。

## 3. 本轮唯一实施的代码修复（其余只记录，不改）

**问题 → 影响 → 根因 → 最小改动 → 回归测试 → 实测改善**

| 项 | 内容 |
| --- | --- |
| 真实问题 | Crossref 增量窗口起点错误（R4） |
| 业务影响 | 6 条 Crossref 检索式每次在 2018 年起的语料上取前 3 页，新沉积文献被历史高相关文献挤出；运行状态仍显示 OK |
| 根因 | 存储的水位线 `2027-02` 是月精度，适配器 `date.fromisoformat` 失败后回退到 2018-01-01；且 `_max_moment` 永不降低，所以永不恢复 |
| 最小改动 | 1）`adapter.usable_incremental_watermark()`：把年/月精度水位线补到该周期的**起点**（保守下界，只会多要不会漏），未来水位线夹到今天；**不改写存储状态**；2）`run_source` 用它生成查询下界，并在运行结果里报告 `watermark_adjustment`；3）`ledger.consistency_check()` 增加 `watermark_in_future` 问题项 |
| 不改什么 | 不改适配器、不改账本状态、不改数据库、不改分类器、不新增来源 |
| 回归测试 | `tests/test_radar_watermark.py`（4 个用例）：只对不可能的水位线生效；运行中适配器看到的都是可用值；存储值保持不变；一致性检查报告该问题 |
| 实测改善 | 真实账本上：修复前 `from-created-date:2018-01-01` → 修复后 `2026-11-16`；全量测试通过 |
| 回滚 | 单个提交，涉及 2 个文件 + 1 个测试文件；回滚不影响数据 |

## 5. 结论

**MedRadar 当前的瓶颈不是"判断不够聪明"，而是"该看的东西没看、看过的东西分不清新旧、分清的东西排不出优先级"。**
这三件事都不需要重写系统：一件是补一个适配器（R1），一件是放宽采集并保持严格准入（R2），
一件是加一个新鲜度闸门和三档重要性（R3）。水位线（R4）已经在本轮以最小改动修好并验证。
