# FIRST PRINCIPLES-001 / 最终决策

- 日期：2026-11-18　｜　作者：独立产品研究负责人（本轮唯一评审者）
- 面向读者：非技术背景的项目负责人
- 证据等级：**A** = 本轮直接测量/可复现；**B** = 单评审判断（方法有偏）；**C** = 他人文档陈述，本轮未复验

---

## 先说结论

**建议：B. NARROW（收窄），不是 CONTINUE，也不是 RECONSIDER。**

一句话：**方向是对的，但现在的 MedRadar 想同时做四件事（论文雷达、监管档案、企业科技树、预测研究），
结果四件都没做成产品。数据基础设施是真的，判断引擎基本可用，但它采的东西不是用户最需要的，
采到的东西分不清新旧，分出来的东西排不出优先级。**

这不是"再做一年就会好"的问题，而是"要先承认产品只该做一件事"的问题。

---

## 1. MedRadar 最本质的用户问题是什么？

用户是一家医疗器械公司 ICU / 床旁监护产品线的研发负责人。他不需要更多信息——
**免费信息已经过剩**。他需要的是：

> 在每周 30 分钟里，知道"哪几件事已经发生、会影响我的产品线、依据在哪"。

这可以拆成三个必要动作：**发现**（该看的都看到了）→ **分级**（知道先看哪个）→ **举证**（能拿给团队看）。

原来的假设是"帮用户发现更多重要技术变化"。本轮实测把这个假设修正为：
**用户最缺的是"分级 + 举证"，而"发现"目前是系统最弱的一环。**

- 证据：`USER_PROBLEM.md`（基于公开资料与实测的任务模型，**无真实用户访谈**）
- 可信度：**B**（任务模型合理但未验证）

## 2. 这个问题是否值得解决？

值得，但只在很窄的一段上成立。

| 值得 | 证据 | 可信度 |
| --- | --- | --- |
| 安全/召回信息值得，因为它是唯一"晚一天就有代价"的信息 | 2026 年一年内，13 个监护产品码下有 **42 行召回记录 = 19 个召回事件**，涉及 Philips / GE / Mindray / Nihon Kohden / Masimo 等；这些信息在 FDA 免费可得，但**没有人为你把它对到你的产品线上** | A |
| 性能证据值得，因为它改变验证方法而不是改变新闻 | 例：ICU SpO2 的灌注混杂、消费级血氧的肤色偏差——都能直接改写验证方案 | A |
| 竞品注册状态值得，但价值较低 | 2026-10 有 2 条监护相关清关（血氧戒指、ECG 算法库） | A |
| "全行业技术情报"不值得（至少现在） | 宽泛的临床论文占绝大多数，研发负责人无法从中获得行动 | B |

**不值得的部分**：把"整条医疗器械行业的技术演化"做成产品。那是咨询公司的工作，不是一个小团队能验证的。

## 3. 当前产品相比现有工具提供了什么真实增量价值？

只有一项被证明，另外几项**目前是反证或不成立**：

| 主张 | 状态 | 证据 | 可信度 |
| --- | --- | --- | --- |
| 证据可核验（每条带原始来源、两种时间、首次发现时间） | **已证明** | 120 条抽样中 100% 可回溯；这是竞品和免费工具的组合里最缺的一环 | A |
| 减少无关内容 | 部分（弱） | 30 天简报 21 条中 20 条属监护技术；但全库判定精确率只有 **0.66** | B |
| 减少检索时间 | 未证明 | 一个分析师用 6 条检索式、两个下午就能复刻它的 PubMed 采集 | A（方法可复现） |
| 更高发现率 | **反证** | 同时期 PubMed 相关文献中，系统只覆盖 **28.5%**（114/400） | A |
| 更强的跨来源关联 | 未证明 | 图谱在真实浏览器里返回 404/500（QA-002）；本轮无法访问部署复验 | C |

结论：**MedRadar 目前的真实增量价值只有"证据可核验"这一条。这条很重要，但单独一条撑不起一个产品。**

## 4. 系统目前最重要的能力是什么？

不是图谱，不是 AI，不是前端，而是**观测账本**：

- 每条记录有：来源、官方标识、首次发现时间、源站公开时间及精度、版本历史、变化状态、
  决策历史（append-only）、证据链接；
- 本轮在隔离环境中验证：新记录入库、同一记录更新产生版本 2 并记录 `changed_fields`、
  来源失败**不推进**水位线、断点可续跑；全量测试通过。

- 证据：`CONTINUOUS_DISCOVERY.md` 第 4 节（合成实验）；`radar/ledger.py`；测试套件
- 可信度：**A**

这是整个项目里唯一"别人不容易复制、而且用户真的需要"的东西。

## 5. 系统最大的三个实际问题是什么？

### 问题一（致命）：最重要的信息根本没采

已上市监护设备的召回，系统里 **0 条**。同期真实存在 **734 条记录**（2026 年 42 行 = 19 个事件），
包括 GE Portrait 软件"可能导致失去监护"、Philips 中央站冻结、Philips 心电工作站数据错误、
Mindray 七个系列说明书召回、Nihon Kohden 中央站网络安全召回。

- 证据：openFDA 实测 + 账本查询；`ROOT_CAUSE_ANALYSIS.md` R1
- 可信度：**A**

### 问题二（致命）：该看的文献没有看

PubMed 只用 7 条固定检索式，每条都强制"ICU"字样。同样 48 天窗口，用更宽的 6 条检索式，
系统只覆盖了 **28.5%**；漏掉的里面至少有 25–30 条是有价值的技术证据，
包括在账本复制前一天发表的一篇 ICU 血压估计论文。

- 证据：`REFERENCE_EVENTS.md` 第 1.1 节
- 可信度：**A**（覆盖率）/ **B**（"25–30 条高价值"是单评审估计）

### 问题三（高）：分不清"新"和"旧"，也排不出优先级

- 系统认为"可进情报流"的 7,360 条里，**7,039 条（95.6%）是两年前的记录**；
- "重要性"这个维度在真实数据里是常量（7,357 条 MEDIUM、3 条 HIGH、0 条 LOW）；
- 8,593 条记录中 **8,588 条是"首次导入"**，所以任何"变化"视图显示的是建库噪声，不是技术变化。

- 证据：账本查询；`INDEPENDENT_EVALUATION.md` 第 6 节
- 可信度：**A**

## 6. 哪些问题来自产品定义，哪些来自算法，哪些来自工程架构？

| 问题 | 来自 | 证据 |
| --- | --- | --- |
| 召回没采 | **产品定义**（没人决定"安全事件必须在范围内"） | 配置文件里写了 recall 路径，但没有适配器 |
| 文献覆盖窄 | **产品定义 + 采集**（谁来定义"我们关注什么"） | 7 条硬编码检索式 |
| 分不清新旧、排不出优先级 | **产品定义**（没有"档案 vs 情报"的概念） | importance 常量；95.6% 归档 |
| 企业树没内容 | **产品定义 + 来源选择** | 36 条标题，2 条相关；Dräger 采的是工业安全板块 |
| 3 条高价值文献被误拒 | **算法**（规则顺序 + 词汇覆盖） | 独立评估 4.2 节 |
| TRANSFER 类基本失效 | **算法** | 一致率 0.17 |
| Crossref 增量空转 | **工程架构**（水位线契约） | 已修复；`2018-01-01` → `2026-11-16` |
| 同作品重复计数 | **工程架构**（存储身份是来源行，不是作品） | 合成实验：同 DOI → 2 条观测 |
| 产品不在 main、九层草稿 | **工程架构（交付）** | main 不含产品 |
| 57k 行文档 | **工作方式** | 文档量 = 代码量 1/3 |

**排序很重要**：前四条是产品定义问题，它们造成的损失远大于任何算法缺陷。
这也回答了任务书开头的问题——**当前最缺的是业务定义，不是代码。**

## 7. 当前已有的 15 万行代码中，哪些能力真正支持核心目标？

先纠正数字：本轮实测为 **154,996 行 Python + 13,181 行 TypeScript/TSX ≈ 168,177 行代码**，
另外有 **57,416 行 Markdown（564 个文件）** 和 478,884 行 JSON。

按"是否直接支持核心问题"分类：

| 类别 | 规模 | 说明 |
| --- | --- | --- |
| **直接支持**（约 15–20%） | 观测账本、适配器引擎、判断引擎、feed API、备份/锁 | 这些是"发现→分级→举证"的实现 |
| **间接支持**（约 10%） | 调度、健康、快照发布、来源注册 | 让上面那部分能持续运行 |
| **当前无用户价值**（约 25%） | 技术图谱、工作台（compare/briefs/review/devices）、企业树 UI | QA-002 已实测其中多个失败 |
| **历史研究资产**（约 50%） | `report.py`(4,145) / `replay.py`(2,842) / `families.py` / `intelligence/*` / `studies/*` / `experiments/` / `research/` | 75 个模块无法从产品入口到达；是项目的研究记录 |

- 证据：`ARCHITECTURE_DIRECTION.md`；代码行数本轮实测
- 可信度：**A**（数字）/ **B**（分类边界）

## 8. 如果只能保留最重要的系统能力，应该保留什么？

**保留四件，其余都可以先冻住：**

1. **观测账本**（append-only + 版本 + 两种时间 + 精度 + 首次发现）；
2. **采集引擎**（水位线、游标、失败不推进、断点续跑）；
3. **判断引擎的 DIRECT / CLINICAL / NON_MEDICAL 三分类**（独立评估 0.84 / 0.84 / 0.36）；
4. **证据详情页 + 来源状态页**（回答"依据是什么""来源是否还活着"）。

可以冻住的：技术图谱、企业树 UI、对比/简报工作台、review ledger、预测研究、论文报告栈。

## 9. 下一阶段最多应该开展哪三项工作？为什么？

**只做三件，按顺序，每件都有验收标准：**

### 工作一：补齐"安全事件"通道（最高优先）

- 内容：openFDA 召回适配器 + 产品码→监护主题映射 + 回填 2024 年以来的历史召回 + 幂等/水位线测试。
- 为什么：唯一"晚一天有代价"的类别，当前覆盖 0%，成本低，收益最大。
- 验收：2026 年的 19 个召回事件（42 行记录）全部在库，且可按事件去重检索；每条能显示"涉及哪个产品码/哪个企业/哪一天"；
  与直接查 openFDA 的结果一致（可复现）。

### 工作二：把"档案"和"情报"分开，并让重要性真的有分级

- 内容：（a）默认简报只收"12 个月内 + DIRECT/TRANSFER"；（b）历史记录进可搜索档案，不进简报；
  （c）importance 从常量变成三档规则（安全事件 / 新注册 / 性能证据）。
- 为什么：没有这三条，扩大采集只会让噪声更多；有了它，工作三才有意义。
- 验收：简报里不再出现 2024 年以前的清关；importance 在真实数据上的分布不再是 99.96% 单一值；
  "变化"视图只显示真实增量（当前 5 条，而不是 8,588 条）。
- 注意：这是**产品决定**，不是代码决定。需要负责人明确回答"档案是否进默认视图"。

### 工作三：一次 4 周前瞻试验，用真实研发负责人验证"周简报"

- 内容：每周一生成 10–15 条候选简报，交给 1–3 位真实研发负责人；记录：
  是否打开、是否点原始链接、是否转发、是否采取了动作、哪几条被判定为噪声、哪一条被判定为"早该知道"。
- 为什么：这是唯一能证明或否定核心价值的方法。本轮所有"用户会喜欢"的判断都是假设。
- 验收（通过标准需事先写定）：例如"4 周内至少 3 周有人打开并点开过至少 3 条原始证据，
  且没有人报告「本周全部无关」"。**如果不达标，应转向 RECONSIDER。**

**明确不做**：不扩到全医疗技术、不重写图谱、不拆 949 行 API、不合并九层 PR、不做本地大模型、
不在同一轮里再改分类器。

## 10. 最终选择：CONTINUE、NARROW 还是 RECONSIDER？

### 选择：**B. NARROW**

| 选项 | 为什么不选 |
| --- | --- |
| CONTINUE（按现方向继续） | 现方向是"论文雷达 + 监管档案 + 企业科技树 + 预测研究"。四件事同时做，每件都没做成产品；继续加功能只会放大"看起来在进步"的错觉 |
| RECONSIDER（暂停、重新定位） | 证据不支持这么重。账本与判断引擎是真的（A 级证据），"证据可核验"这一条增量价值已被证明，安全事件通道只需要一个适配器。**有机会，只是被范围拖住了** |
| **NARROW（收窄）** | 把范围收窄到**一个主题（监护设备的安全与性能证据）+ 一个输出（周简报）+ 一个验证（4 周前瞻试验）**，其余冻结 |

### 收窄后的目标边界（写清楚，避免又扩散）

| 收 | 放 |
| --- | --- |
| 主题：已上市监护设备的安全、性能、注册状态 | 全医疗技术、影像/介入/牙科、临床疗效研究 |
| 来源：openFDA（清关+召回）、PubMed（宽检索+严格准入）、1–2 家企业官方 | 专利、招聘、财报、社交、全行业新闻 |
| 输出：周简报（10–15 条）+ 证据详情 + 来源状态 | 知识图谱、企业科技树、对比工作台 |
| 用户：一个产品线的研发负责人 | 全公司、销售、投资 |
| 证据：每条可回溯到原始来源与时间精度 | 预测、评分、置信度排名 |

### 什么情况下我会改变这个判断

| 如果出现 | 那么 |
| --- | --- |
| 4 周试验中，负责人每周主动打开并至少点开 3 条原始证据 | 可以把 NARROW 升级为 CONTINUE（收窄版），并开始第二主题 |
| 4 周试验中，多数周无人打开，或反馈"全是噪声" | 应转为 **RECONSIDER**，先回到问题定义 |
| 出现了真实的付费意愿（哪怕是内部预算） | 说明方向成立，可以加大投入 |
| 补齐召回后，用户仍说"这些我知道" | 说明增量价值不在"发现"，而在"举证"，产品形态应改成证据库 |
