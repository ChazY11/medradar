# FIRST PRINCIPLES-001 / 第七阶段：MedRadar 应该保留什么

- 依据：业务验证（USER_PROBLEM）、独立标准、独立评估、根因排序。
- 本轮**只给收敛建议**，不做大规模删除。
- 判别原则：**必要的领域复杂度可以保留；重复、隐式和没有用户价值的复杂度应当消除。**

## 0. 先说结论：三条路线的取舍

| 路线 | 内容 | 判断 | 理由 |
| --- | --- | --- | --- |
| 历史科研与预测研究 | 论文/预测/事件研究（PR #1–#45 的大部分） | **ARCHIVE** | 是项目的研究记录，不是产品路径；不能删，但停止扩展 |
| 数据基础设施 | 账本、适配器、快照、调度、备份 | **KEEP（其中雷达账本是核心）** | 唯一具备时间语义与可追溯性的资产 |
| 商业医疗技术情报产品 | 简报、企业树、图谱、工作台 | **NARROW** | 方向成立，但当前形态过宽、输入不足、输出未被验证 |

## 2. 任务书点名的六个问题，逐个回答

### 2.1 三套事实来源是否真的都需要？

**不需要三套。** 现状：

| 存储 | 入口 | 权威内容 | 时间语义 |
| --- | --- | --- | --- |
| `data/medradar.sqlite`（legacy） | `python -m medradar collect/analyze/report` | FDA 批准 + 市场信号 + 纸面交易 | 弱 |
| `product/snapshot/*`（PRODUCT-001..004） | `medradar web` → `/api/events` | FDA 510(k)/PMA/召回的结构化快照 | 单快照，无观测历史 |
| `data/radar/radar.db`（RADAR-001） | `radar api` → `/api/radar/feed` | 多源观测账本 + 版本 + 决策 | **完整**（首次发现/公开时间/精度） |

判断：**只有第三套具备"情报"所需的时间语义**。第一套是研究记录（ARCHIVE），
第二套与第三套在 FDA 数据上重复，且第二套没有"何时发现"的概念（SEPARATE，作为内部核查工具）。
不建议本轮合并——迁移需要快照重建与浏览器 E2E，风险大于收益；但**不应再向第二套增加功能**。

### 2.2 两个组织注册表是否有不同职责？

**没有本质区别，只有规模区别。** `config/radar/organizations.json` 是 3 个焦点企业（philips / ge_healthcare /
draeger，4,993 字节）；`medradar/product/identity/organizations.json` 是 59 个申请人（454,117 字节）。
两者 id 体系不同，同一个 Philips 在两处是不同主键。

判断：**SIMPLIFY 为一个注册表**（雷达的 3 个焦点企业是"关注列表"，不是"身份表"；身份表应该只有一份）。
本轮不做，因为迁移会改变图谱与快照的 id，需要一次数据迁移。

### 2.3 两个前端入口是否都是现阶段产品所需？

**不是。** `/api/events`（快照工作台）与 `/api/radar/feed`（雷达）互不共享契约，
QA-002 已实测：公网导航被裁剪为"实时雷达 + 科技地图"，旧工作台地址全部 302 到 `/radar`。
也就是说，**产品实际上只剩一个入口，但代码里还维护着两个**。

判断：**保留 `/api/radar/feed` 为唯一产品入口**；工作台降级为内部核查工具（SEPARATE）。

### 2.4 知识图谱是否创造了实际用户价值？

**本轮没有找到证据。**

| 观察 | 证据 |
| --- | --- |
| 首次建库即产生 17,686 条断言"变化" | QA-002 实测 `/graph/changes` 返回 17,686 条，只列 300 条 |
| 图不是技术树 | QA-002："技术主题 → 企业 → 产品或记录 → 证据"，没有代际、没有路线演进 |
| 证据节点打不开 | QA-002：`/graph/node` 404（`obs:` 前缀被前端剥离） |
| 能力语义错误 | QA-002：把 `TOPIC_RELATED` 显示为 1 capability |
| 图谱规模与内容的比值 | 22,991 节点 / 17,686 边，但同期情报池只有 21 条/30 天 |

判断：**SEPARATE（保留为探索视图，移出产品核心与发布门槛）**。
如果未来要恢复，前提是先有"产品代际/能力时间线"的数据模型，而当前连输入（企业产品谱）都没有（R5）。

### 2.5 876 行 assessment 模块是否需要拆分？

**不需要。** 拆分是按文件大小排序的结果，不是业务判断：

- 它是一个"六维判断 + 一条决策策略"的单一职责实现；
- 独立评估显示它的 DIRECT/CLINICAL 判断是可用的（0.84），瓶颈在采集与分级（R1–R3）；
- REF-004 已把重复实现（`relevance.py` 421→96 行、适配器内的第二套过滤）消除，
  **现在全系统只有一套相关性规则**——这是正确方向，拆分不会改善任何用户可见结果。

### 2.6 九层 Draft PR 的维护成本

| 事实 | 数值 |
| --- | --- |
| `main` 是否包含产品 | **否**（`main` = 86311b1，PR #41 合并） |
| 栈 | #46 → #47 → #48 → #49 → #50 → #51 → #52 → #53 → #54，严格线性，全部 open |
| `refoundation/004` | 本地分支（不在 origin），#54 之上 9 个提交 |
| 相对 main 的规模 | 662 个文件，+187,080 / −1,037 |
| 评审单位 | 一次要审 18 万行，或信任"分层"叙事 |

判断：**这是真实的维护成本，也是真实的交付风险**（产品不在 main = 没有正式产品）。
建议（不属本轮授权）：先合并一层"最小可用"到 main（账本 + 简报 + 来源状态），
把图谱、工作台、研究资产留在草稿。**不要试图一次合并九层。**

## 3. 哪些复杂度是真实业务需要的，哪些是历史的

| 复杂度 | 性质 | 判断 |
| --- | --- | --- |
| append-only 账本 + 版本 + 变化状态 | **真实**（可追溯是核心卖点） | 保留 |
| 水位线/游标/断点续跑/单写者锁 | **真实**（持续采集的必要条件） | 保留 |
| 六维判断（来源/领域/相关性/实体/新鲜度/重要性） | **真实**（否则一个标签承载八个判断） | 保留，但 importance 必须真的分级 |
| 快照原子发布 + 备份 | **真实**（生产必需） | 保留 |
| 三条并行车道 | **历史**（每轮加一条而非统一契约） | 收敛 |
| 两个组织注册表 | **历史** | 合并 |
| 两个前端入口 | **历史** | 收敛为一个 |
| 位图断言图谱 | **历史**（技术驱动，非需求驱动） | 移出核心 |
| 57k 行文档 / 564 个文件 | **历史**（过程证明） | 收敛到"产品说明 + 决策记录" |
| 九层草稿栈 | **历史**（每轮加一层） | 先合并最小可用层 |

## 4. 一句话给负责人

**MedRadar 真正值得保留的，是一个"能记住每一条信息何时被发现、原始证据是什么"的观测账本；
真正需要砍掉的，是围绕它长出来但还没有用户的三层外壳（图谱、工作台、研究栈）。**
