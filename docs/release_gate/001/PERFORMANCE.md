# RELEASE-GATE-001 / 性能与资源实测

- 测试机：**生产服务器本身**（2 vCPU / 3,724 MB / SATA SSD），与其他生产服务同时运行
- 原则：**只在同等数据规模下比较代码**。不同数据量的两个版本之间不做"性能提升/退化"的结论。
- 结论：**候选版本没有可测量的性能退化**；唯一的变化来自**数据变多**（召回通道），那部分单独量化。

---

## 1. 迁移成本（一次性）

| 指标 | 值 |
| --- | --- |
| v2→v3 迁移（8,360 条观测） | **0.58 s**（进程内计时；含解释器启动 0.75 s） |
| 迁移后账本体积 | 45,268,992 B → 52,322,304 B（**+15.6%**） |
| 第二次打开（不再迁移） | 0.011 s |

> 上一轮曾报告"迁移让库增长 66%"，那其实是"迁移 + 全量重判"的合计。本轮把两者分开测了。

---

## 2. 管道（advance）在各场景下的耗时

| 场景 | 数据量 | 批次 | advance 耗时 | wall | 结果 |
| --- | --- | --- | --- | --- | --- |
| 迁移后首次（含 6,563 条召回入库 + 图谱物化 33,175 条断言） | 14,923 | 18 | 139.4 s | 抓取 87 s + 管道 139 s | CONVERGED |
| 幂等重跑 | 14,923 | 1 | 0.21 s | 2.36 s | CONVERGED，admitted=0 |
| 全源强制周期（新增 1,330 条） | 14,923 → 16,253 | 42 | 31.1 s | 111 s | CONVERGED |
| 单源无新数据 | 16,253 | 1 | 0.21 s | 1.27 s（抓取） | CONVERGED，NO_NEW_RECORDS |
| reproject（无需重判） | 16,253 | — | < 1 s | — | decided now = 0 |

**关键读法**：`advance` 的成本几乎全在"有多少新观测要物化进图谱"，而不是"库有多大"。
幂等重跑 0.21 s 证明了这一点——16,253 条观测的库，没有新工作时只花一次查询的时间。

### 2.1 图谱物化的真实成本

一次 6,563 条新观测的物化会产生 **33,175 条断言**（含 3,783 条重复），耗时约 130 s，
也就是说 **每 1,000 条新观测约 20 s**（本机）。这是候选版本最重的单步操作，且在 2 vCPU 上近似线性。

## 3. API 延迟

在隔离实例（staging，16,253 条观测 / 45,174 节点图谱）上，每个端点 12 次采样：

| 端点 | p50 | p95 | p99 | 备注 |
| --- | --- | --- | --- | --- |
| `/api/radar/feed?limit=20` | 131 ms | 142 ms | 406 ms | 首次 406 ms 是冷缓存 |
| `/api/radar/feed?limit=20&scope=latest&days=7` | 131 ms | 137 ms | 138 ms | 窗口过滤没有额外成本 |
| `/api/radar/sources` | 101 ms | 129 ms | 284 ms | 含 7 个来源的延迟统计 |
| `/api/radar/graph/summary` | **2,491 ms** | 2,533 ms | 2,649 ms | 见 §4 |
| `/api/radar/health`（冷） | 3,442 ms | — | — | 六项检查 + 资源快照 |
| `/api/radar/health`（15 s 缓存命中） | **2.3 ms** | — | — | 前端首屏走缓存 |

### 3.1 与生产对比（数据量不同，不能直接比较）

| 端点 | 生产（部署版，8,360 条 / 23,146 节点） | 隔离（候选版，16,253 条 / 45,174 节点） |
| --- | --- | --- |
| `/api/radar/health`（冷） | 1,371 ms | 3,442 ms |
| `/api/radar/feed` | 92 ms | 131 ms |
| `/api/radar/graph/summary` | 1,153 ms | 2,491 ms |

两侧数据量差一倍，这三组数字**不能**用来判断"候选版本更慢"。§4 给出分离实验。

## 4. 分离实验：代码 vs 数据（2×2）

同一台机器、同一份 taxonomy、只读打开，各 5 次取中位：

| 代码 \ 数据 | 生产图谱（23,146 节点） | 隔离图谱（45,174 节点） |
| --- | --- | --- |
| **部署版**（`14eaf61`） | 1,153 ms | 2,305 ms |
| **候选版**（`f2f70dd`） | 1,167 ms | 2,321 ms |

- 代码效应：+1.2%（生产数据）/ +0.7%（隔离数据）→ **可忽略**
- 数据效应：**+100%**（节点数翻倍 → 延迟翻倍）

结论：`/graph/summary` 的 2.5 s **不是候选版本引入的**，是召回通道让图谱从 2.3 万节点涨到 4.5 万节点。

**给产品的判断**：这个端点不是首屏关键路径（首屏用 `/health` 缓存 + `/feed`），但 2.5 s 已经
影响"科技地图"页的可用性。建议在回填后的第一周观察，必要时加缓存（该端点当前没有 TTL 缓存）。

## 5. 内存与磁盘

| 指标 | 值 | 说明 |
| --- | --- | --- |
| 隔离 Web 常驻 RSS | **195 MB** | 未挂载 FDA 快照目录 |
| 生产 Web 常驻 RSS（部署版） | 468 MB | 挂载了 FDA 快照（`--data-dir /srv/medradar/data/fda`） |
| `radar verify` 峰值 RSS | 314 MB | 一次性命令 |
| `radar status` 峰值 RSS | 317 MB | 同上 |
| 周报生成峰值 RSS | 151 MB | 7 天窗口 |
| 迁移 + 首次 advance 峰值 | < 320 MB | 与上面同一量级 |
| 隔离数据目录 | 409 MB（radar.db 285 MB + graph.db 125 MB） | 含 6,563 条召回回填 |
| 召回回填对账本的增量 | **+206 MB**（其中 payload 125 MB，平均 19.5 KB/条） | 最大的单项增长 |
| 服务器可用内存（隔离 Web 运行时） | 1,496 MB / 3,724 MB | 与生产服务并存 |

**切换后的内存预期**：候选版 Web 会像现在一样挂载 FDA 快照，所以常驻内存应与今天的 468 MB 相当，
而不是隔离环境的 195 MB。加一个调度器（约 39–50 MB），总量仍在 640 MB/768 MB 的 cgroup 上限之内。

**磁盘预期**：生产 `data/radar` 现在 374 MB（含备份与演练副本）。切换 + 召回回填后约为
285 MB 账本 + 125 MB 图谱 + 备份 ≈ 700 MB–1 GB。磁盘 44 GB 可用，**没有压力**，
但备份保留策略（14 份）会随账本变大而变大，需要按 §6 观察。

## 6. 长期负载评估

| 项 | 实测/推算 |
| --- | --- |
| 常规采集节奏 | 131 条/天（实测 36 小时内 131 条增量） |
| 每条新观测的图谱成本 | 小批量约 20 ms；大批量约 20 s/1,000 条 |
| 每日账本增长 | 131 条 × 混合 payload（召回 19.5 KB、文献 1–3 KB）→ **约 1–3 MB/天** |
| 每周备份增长 | 保留 14 份 → 稳态约 2 倍账本大小 |
| WAL | 实测 4.1 MB 未 checkpoint，属正常；`synchronous=NORMAL` |

按这个速率，账本一年增长约 0.4–1 GB，磁盘 44 GB 足够；真正的把关点是**备份保留策略**与
**召回通道每月的回填量**（若某月 FDA 集中发布，单次可能 +50 MB）。

## 7. 会不会拖垮同机的其他服务

| 风险 | 实测 | 判断 |
| --- | --- | --- |
| 隔离 Web（195 MB）+ 生产 Web（468 MB）+ 调度器 | 总内存 1,888 → 2,227 MB，available 仍有 1,496 MB | 安全 |
| 迁移 / advance 峰值（`320 MB） | 发生在启动阶段，无并发大查询 | 安全 |
| 图谱物化 130 s 的 CPU | cgroup `CPUQuota=70%` 生效，Nice=10 | 会拖慢但不阻塞 |
| 磁盘 | 44 GB 可用 | 安全 |

**结论**：这台机器能同时承受旧服务与完整候选服务；但**不建议长期并存**——
隔离环境只用于验收，切换后应当关掉（见 `RELEASE_RUNBOOK.md` §7）。
