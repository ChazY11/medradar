## 我们这次到底搞清楚了什么

### 1. 服务器上跑的是哪个版本？

**14eaf61（内部代号 QUALITY-001）。**

怎么确认的：不是看一个写着版本号的文本文件（那只能算线索），而是把服务器上那 1,759 个代码文件
逐个算指纹，和本地这个版本的代码比对——**1,759 个全部一致，一个不差**。
再检查运行中的进程实际加载的是哪个目录里的代码，也一致。

### 2. 线上和"验收过的新版本"差在哪？

差 17 个提交，最关键的三处：

| 缺什么 | 后果（用大白话） |
| --- | --- |
| **没有 FDA 召回通道** | 线上数据库里召回记录是 **0 条**。也就是说：Philips 那次"转运中断开中央监护"、Nihon Kohden 那次"中央站漏洞可能中断多床报警"——**这些线上根本采不到**。 |
| **水位线不会自愈** | 采集进度标记一旦写错（比如写成"未来"），线上版本不会发现也不会修正，会一直错下去，而且**没有任何提示**。 |
| **健康检查只看旧工作台** | 现有的定时检查只探 8787 端口（旧工作台）。雷达（8791）和调度器就算全停了，检查依然报绿。 |

### 3. 数据能不能安全升级？

**能。** 在生产数据的副本上实测：**0.58 秒**完成，8,360 条记录一条不少，判定历史一条不改
（旧的保留、新的追加），数据库只增大 15.6%。

**而且我们在这个环节发现了一个会导致"永久丢判定"的严重缺陷，并修好了：**
如果升级过程中机器被重启/杀掉，旧代码会留下一个"看起来已完成、实际没搬完"的数据库，
之后**每次打开都认为已经升级好了**——8,360 条判定会永久不可见，而且不报错。
修好之后，重新打开就会自动补完。这条有专门的测试守着。

### 4. 备份到底靠不靠得住？

**靠得住，而且我们是真恢复了一遍才这么说的。**

- 备份是用数据库官方的"在线备份"接口做的（不是复制文件——那样会丢掉 4 MB 还没落盘的数据）。
- 恢复演练：把备份还原到另一个目录，检查完整性（ok）、核对 8,360 条、抽查一条记录的内容指纹
  （完全一致）、再用**线上正在跑的代码**起一个临时服务读它（接口全部正常）。
- 另外存了一份到这台服务器之外，指纹一致。

### 5. 升级失败能不能退回去？

分两种情况：

- **还没真正切换就发现问题** → 直接关掉新服务，生产一动没动。**零损失。**
- **已经切换、新版本已经写过数据** → 可以退，但必须"代码 + 数据"一起退，
  而且会丢掉**切换后那段时间的"首次发现时间"**（几小时通常不到 10 条记录）。
  数据本身可以重新采集回来，但"我们是什么时候第一次知道这件事的"这个时间戳回不来了。

这一点必须你知情并接受，所以它是一条放行条件。
