# RELEASE-GATE-001 / 数据一致性方案（切换窗口）

- 核心结论：**切换不搬运数据。** 正确的切换是"就地迁移生产库"，不是"用候选库覆盖生产库"。
  一旦接受这个前提，所谓"切换窗口的数据差异"就只剩下一个 60 秒的写入冻结。
- 本节给出可执行的流程、验证查询，以及"如果非要搬运会失去什么"的分析。

---

## 1. 问题的真实形状

候选环境是拿 18:51Z 的备份建的。生产却在继续运行。两者之间会不会分叉？

实测（18:51Z 备份 vs 19:15Z 生产）：

```
                  backup   live   delta
observations       8360    8360     0
versions           8360    8360     0
changes            8360    8360     0
mappings           8360    8360     0
admissions         8360    8360     0
newest first_observed  2026-11-18T18:24:45Z（两者相同）
newest success         2026-11-18T18:24:46Z（两者相同）
```

**这次漂移是 0，但那是运气**：调度器在 18:24 刚跑过，下一次 pubmed 在 00:24、crossref 在 00:24、
openFDA 在 00:17。也就是说 18:51 到 19:15 之间**恰好没有到期的来源**。

所以不能拿"这次没变"当机制。机制必须能在"备份之后生产又写了几百条"的情况下依然正确。

---

## 2. 三种方案，以及为什么选第三个

| 方案 | 做法 | 数据风险 | 判断 |
| --- | --- | --- | --- |
| A. 用候选库覆盖生产 | `cp staging/data/radar.db → data/radar/radar.db` | **丢掉备份之后生产写入的所有观测**；把测试期间的强制采集混进生产；候选库的 `first_observed_at` 有一部分是测试时刻 | **否决** |
| B. 把候选库的新行"补丁"进生产 | 导出候选多出的行，重放进生产 | 需要自己实现一套去重/合并，且 `observation_id` 是内容寻址的，重放会产生"看起来一样但时间戳不同"的行 | 否决（复杂且无收益） |
| C. **就地迁移生产库** | 迁移是 v2→v3 的**结构**变更，不是数据搬运；生产库自己变成 v3 | 无数据丢失（迁移不删行）；不需要对账 | **采用** |

方案 C 的关键事实（本轮已实测）：

- 迁移只改结构 + 把旧判定复制到新表，**不删除任何观测**；
- 迁移耗时 **0.58 s**（8,360 条）；
- 迁移是幂等的，重复打开不会再迁移；
- 迁移后的 v3 库可以被候选代码正常读写（`advance`/`reproduce`/API 全部通过）。

**候选环境的价值是"证明迁移和候选代码在真实数据上没问题"，不是"提供一份要搬过去的数据"。**

---

## 3. 切换窗口的写入冻结（唯一需要的"对账"）

### 3.1 冻结多长

| 步骤 | 实测耗时 |
| --- | --- |
| 停调度器（`systemctl stop`） | < 1 s（`TimeoutStopSec=120` 是上限，不是常态） |
| 一致性备份（`radar backup`） | 0.35 s（8,360 条）；本轮 45 MB 约 0.4 s |
| 启动新 Web（首次打开触发迁移） | 迁移 0.58 s + 应用启动 `2 s |
| 启动新调度器 | < 2 s |
| **合计冻结** | **< 10 s**（保守按 60 s 计划） |

在 6 小时（pubmed）与 12 小时（crossref）的 cadence 面前，10 秒的冻结不会漏掉任何一次采集。

### 3.2 冻结期间会发生什么

- 没有来源被轮询 → 没有观测产生 → 没有"窗口内数据"需要事后补。
- 即使有（例如切换时正好有一次采集在飞），它写的行会落在**同一个库**里：
  切换前后是同一个 `radar.db` 文件，只是 schema 变了。不存在两份数据要合并。

### 3.3 切换后第一次采集

新调度器起来后，第一个周期会看到与切换前完全相同的 `source_state`（水位线、`last_checked_at`
都在库里），所以：

- 不该跑的来源不会跑（未到期）；
- 该跑的来源会用**同一个水位线**跑，不会重头抓；
- 即使重复抓到同一条记录，账本身份是 `(source, source_record_id)` + `content_hash`，
  结果是 `UNCHANGED` 或 `UPDATED`，**不会产生重复行**。

这条已实测：对同一个来源连跑两次，第二次是 `NO_NEW_RECORDS, 0 new, 266 unchanged`。

## 4. 切换后的对账清单（15 分钟）

每一步都给出期望值与失败时的动作。

| # | 检查 | 期望 | 失败动作 |
| --- | --- | --- | --- |
| 1 | `SELECT COUNT(*) FROM observation` | 与切换前完全相同（本轮 8,360） | 立即回滚（路径 B） |
| 2 | `SELECT value FROM meta WHERE key='schema_version'` | `radar-ledger-v3` | 回滚 |
| 3 | `SELECT COUNT(*) FROM observation_admission WHERE rules_digest='legacy-v2'` | = 切换前判定数（8,360） | 回滚（说明迁移没搬完） |
| 4 | `SELECT COUNT(*) FROM observation o LEFT JOIN admission_current a ON a.observation_id=o.observation_id WHERE a.observation_id IS NULL` | 0 或等于"待判定"数 | 跑一次 `radar reproject` |
| 5 | 各来源 `watermark` | 与切换前一致 | 记录并调查（迁移不该改水位线） |
| 6 | `radar verify` | `integrity: OK`（水位线告警允许存在） | 回滚 |
| 7 | `radar advance` | `CONVERGED`，`admitted` ≈ 观测数（重判），耗时 `12 s | 观察 backlog；若 `STALLED` 则回滚 |
| 8 | `/api/radar/health` | 200，`state` 为 HEALTHY 或 DEGRADED（水位线） | 回滚 |
| 9 | `/api/radar/feed` | 200，条目数合理 | 回滚 |
| 10 | `radar brief --since … --until …` | 生成成功，含"历史安全事件补充"章节 | 不需回滚（只读） |

**第 7 步的期望值很重要**：迁移后第一次 `advance` 会为每条观测追加一条 v3 判定
（`admitted ≈ 8,360`），这是**一次性**的，之后每次都是 0。如果看到"每次 advance 都在增加"，
说明判定没有收敛——立刻回滚。

## 5. 召回通道回填：一个独立的、可选的决策

切到候选版本后，`openfda_recall` 这个来源在 `source_state` 里**不存在**（生产 v2 库没有它）。
第一轮调度会把它当作"从未运行"的来源，于是做一次初始化采集。

这一次采集的规模必须提前知道：

| 实测（隔离环境） | 值 |
| --- | --- |
| 首次召回采集 | 6,563 条，31 个 scope，87 s |
| 数据体积 | 账本 +206 MB（其中 payload 125 MB，平均 19.5 KB/条） |
| 公开日期跨度 | 2003-03-05 .. 2026-11-05（23 年历史） |
| 图谱增长 | 15.5k → 45.2k 节点；`/graph/summary` 1.2 s → 2.3 s |
| 回填标记 | 全部 `BACKFILLED` + `HISTORICAL_BACKFILL` + 显式理由 |

所以发布决定必须包含一个显式选择：

- **选项 1**：切换后让调度器自然做首次召回采集（默认行为，无需额外操作）。
- **选项 2**：切换时先不启用召回通道（`enabled=false`），等磁盘/图谱性能评估后再开。
- **选项 3**：切换后立即手工回填，并在当天观察磁盘与 API 延迟。

推荐 **选项 1**，但必须在切换后的观察期里盯住磁盘与 `/graph/summary` 延迟（见 `PERFORMANCE.md` §5）。

## 6. 如果还是想用候选库（不推荐）

如果因为某种原因必须"把候选库搬过去"，那么至少要做这些事，并且接受损失：

1. 记下候选库的构建时刻与来源备份 sha256；
2. 对比生产与候选的 `observation_id` 差集（候选独有 / 生产独有）；
3. 生产独有的行必须导出并重放（否则丢失）；
4. 候选里"测试期强制采集"的 1,330 条要决定是否保留（它们是真的，但是测试驱动的）；
5. 重新计算 `first_observed_at` 的语义（候选里有一部分是测试时刻）；
6. 迁移后重跑 `advance`。

—— 这六步里任何一步出错都会产生"看起来对、但时间语义错了"的账本。而方案 C 一步都不需要。

---

## 7. 小结

- 切换 = **停写 10 秒 + 就地迁移 + 起服务**，不是数据搬运。
- 因此不存在"切换窗口内的观察丢失"问题。
- 唯一需要提前决策的是**召回通道首次回填的规模**（+206 MB、+29.7k 图谱节点）。
- 对账清单 10 项，任何一项不符即回滚；回滚的数据代价见 `BACKUP_AND_RESTORE.md` §5.2。
