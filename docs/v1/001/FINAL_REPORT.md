- 本地提交：3 个（`300a864` 召回通道、`64c3599` 情报语义、`0d6a5bd` 交付与证据）

## 先说结论

**方向成立，但只在一个很窄的位置上成立：已上市监护设备的安全事件。**
本轮把这条通道从 **0 条** 做到了 **626 个监护召回事件**，把「档案」和「本周情报」真正分开，
并生成了第一份**每一条都能点回官方记录**的候选周报。
四周用户试验的机制已经就绪，但**还没有任何真实用户**，因此**不能**说产品价值已被验证。

## 1. 本轮到底实现了什么

| 之前 | 之后 |
| --- | --- |
| 账本里 **0 条**监护设备召回 | **6,563 条**召回观测 = **2,330 个 FDA 召回事件**，其中 **626 个**是监护设备 |

| 历史导入可能被包装成新闻 | **回填 = BACKFILLED**，历史首次采集单独一节，绝不写成「本周新发生」 |
| 没有任何用户验证机制 | 四周方案、反馈表、独立对照流程、自动指标（含分母） |

## 2. 现在真正可以交付的监护情报是什么

**第一条**：已上市监护设备的安全行动，且能追到 FDA 官方记录。本轮核实并逐字段对源验证了 8 个事件，例如
Philips 中央监护（PIC iX）连接中断、Nihon Kohden CNS-6200 中央站空指针漏洞、GE Portrait 软件可能导致失去监护、
Mindray ePM/BeneVision 说明书报警措辞不足。

**第二条**：监护性能证据（血氧在不同活动与肤色下的偏差、外周灌注对血氧准确性的影响、脑氧监护的临床应用边界）。

**第三条（本轮明确的限制）**：以上两条都在**周报窗口内**才有「本周」意义。
本期窗口（2026-10-19 至 2026-11-18）内**没有**新的监护召回公开发布，
所以本期真正重要的安全信息以「**历史安全事件补充**」的形式出现，共 5 条，全部为 CRITICAL，并明确标注不是本周新发生。

## 3. 还有哪些重要事件发现不了

| 缺口 | 影响 |
| --- | --- |
| **中国 NMPA、欧盟 MDR / EUDAMED、Health Canada** | 只在这些辖区发布的安全行动完全不可见 |
| **企业官网** | GE HealthCare 的 robots.txt 拒绝自动访问（系统正确标记为「访问受限」，不是「没有新闻」）；Philips / Dräger 官网内容与监护相关性很低 |
| **产品型号 ↔ 我的设备** | 系统能告诉你「某型号被召回」，但**还不能**自动判断这是不是你在支持的型号 |
| **文献覆盖** | PubMed 仍然只有 7 条固定检索式（FIRST PRINCIPLES-001 实测覆盖 28.5%）；本轮没有改 |
| **FDA 网页本身** | 本机访问被反爬拦截，用户点「原始链接」可能看不到页面 |

## 4. 历史档案是否已经和正式情报分开

**是。** 判定方式（不是主观感觉）：

- 窗口内有变化、但不够交付标准的记录 → `CANDIDATE`（本期 462 条），并写明缺哪一条；
- 窗口内没有变化的记录 → `ARCHIVE`（本期 14,674 条），可搜索、可追溯，不进周报；
- 历史记录即使本周第一次被采到，也**不会**被写成「本周新发生」：本期 14,771 条属于这一类，
  其中只有 5 个重要安全事件被放进「历史安全事件补充」；
- 本期周报正文的 15 条，没有一条是 2024 年以前的清关记录（对比：上一版本的默认视图里 95.6% 是两年前的档案）。

## 5. 重要性分级是否具有实际意义

**是，而且可以检查。** 本期在真实账本（15,156 条）上的分布是：

| 级别 | 数量 | 典型触发 |
| --- | --- | --- |
| CRITICAL | 165 | 仍在生效的监护设备召回，且官方原因写明会失去监护/报警失效/数值错误/冻结/伤害 |
| HIGH | 292 | 仍在生效但没有写明后果的召回（291）+ 30 天内评估测量本身的性能研究（1） |
| MEDIUM | 1,069 | 12 个月内的监护监管决定 / 直接相关的监护记录 / 需复核的新记录 |
| LOW | 13,630 | 历史档案、日期不明、非监护范围 |

三条防止「为了好看而分级」的规则：不按比例分配；单例/病例报告不能到 HIGH；综述/评论不能到 HIGH（系统综述除外）。
每条记录都带 `importance_reasons`，可逐条检查。

## 6. 持续采集是否得到真实验证

**部分验证，必须说清楚边界。**

已验证：

- 采集、入库、去重、回填标记、增量周期都真实跑过：回填 138 秒采集 6,563 条；
- 重复采集不产生新记录（0 新增，1,481 / 266 条未变）；清单完成后一个周期只需 **2 次请求、4.3 秒**；
- 失败不推进水位线；试运行不再留下假的「运行中」记录；
- 已知的 Crossref「未来水位线」缺陷现在会被**明确报错**（`radar verify` 失败并指出 `crossref`），不再假装健康。

**未验证**：窗口内没有新的监护召开发布，所以「新事件能否在 X 小时内被发现」**没有**被证明。
另外发现一个既有缺陷：`radar run` 的 `advance` 阶段在 1.5 万条语料上 25 分钟未收敛；
本轮用「采集与判定分开执行、判定幂等」绕开，并把根因记录在 `INCREMENTAL_RELIABILITY.md`（下一轮第一优先）。

## 7. 第一份周报是否可供人工审阅

**可以**，并且已经生成了：`WEEKLY_BRIEF_001.md`。它包含：

- 15 条正式情报（每条：标题、事件日期与精度、系统发现日期、来源与原始链接、涉及设备与企业、发生了什么、为什么与监护有关、重要性及理由、研发关注点、不确定性、复核状态、字段依据）；
- 6 条待人工复核；5 条历史安全事件补充；本期被排除内容的计数与原因；方法与限制。

**但没有任何真实用户或人工评审者看过它。** 复核状态字段如实写着 `not reviewed` 或
`checked against the official record by the agent; not a human review`。

## 8. 四周试验是否已经具备启动条件

**机制**已经具备：周报、反馈表、独立对照流程、指标（含分母）、停止/收窄的预登记标准。
**人**还没有：0 位真实用户。因此试验状态是 **NOT STARTED**，
任何「用户会喜欢」「每周都会看」的说法都**没有**证据。

**结论：可以启动，前提是先招到 1–3 位 ICU / 床旁监护产品线的真实研发负责人。**

## 9. 是否出现新的架构复杂度

**没有第二套系统。** 具体：

- 新增 3 个模块（1 个适配器 329 行、1 个筛选规则 258 行、1 个派生视图 913 行）；
- **没有新表、没有数据库迁移、没有新服务、没有新前端、没有新分类引擎**；
- 复用：Adapter 契约、账本五张表、判定表（追加式）、REFOUNDATION-004 的维度、产品码与企业注册表、API 结构；
- 新增的代价：`assessment.py` 依赖 `recall.py`（单向）；`intelligence.py` 913 行偏大，若试验继续应拆分。

## 10. 当前是否建议进入真实用户试验

**建议进入，但只能是「能否被真实用户使用」的试验，不是「商业价值已被证明」的结论。**
理由：

- 安全事件通道从 0 到 626 个事件，是真实增量；
- 8 个关键事件逐字段与实时官方 API 一致，是可核实性；
- 周报已经把「本周」与「历史」分开，不再用档案冒充新闻；
- 但**没有任何证据**表明研发负责人会读、会信、会因此改变行动。这正是四周试验要回答的唯一问题。

## 13. 一句话给决策者

**我们现在知道这个产品只该做一件事：把已上市监护设备的安全与性能变化，每周变成 10–15 条能点回官方记录的情报。**
这一轮证明了它在技术上做得到，也把自己的边界（哪些事件永远看不到）写清楚了。
它还**没有**证明有研发负责人愿意读它。下一步不是加功能，而是找 1–3 个人，跑四周。
