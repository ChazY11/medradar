# V1-001 / PILOT PROTOCOL — 四周真实用户验证

- 状态：**NOT STARTED**（本轮只准备机制，没有开始任何一周，也没有任何用户反馈）
- 目标读者：项目负责人、未来的评审者
- 关联文件：`WEEKLY_BRIEF_001.md`（首期候选周报）、`PILOT_FEEDBACK_TEMPLATE.csv`、`_evidence/reference_events.json`

## 1. 要验证的假设，以及什么会推翻它

**假设 H1**：一位 ICU / 床旁监护产品线的研发负责人，每周花不超过 30 分钟阅读这份周报，
能获得**至少一条此前不知道、且可以据以行动或转发的监护安全/性能信息**。

**推翻条件**（任何一个成立即视为 H1 不成立）：

1. 连续 2 周无人打开周报，或无人点开任何原始证据链接；
2. 4 周内被认为「有价值且新」的条目数 ≤ 1；
3. 用户明确表示「这些我都已经知道」或「与我无关」占半数以上；
4. 维持一期所需的人工复核时间持续超过 2 小时。

本轮**没有**任何用户数据。上述阈值是**事先登记**的，不允许在试验结束后修改。

| 项 | 要求 |

## 3. 每周固定流程（4 周，每周同一节奏）

| 时点 | 动作 | 负责人 | 产物 |
| --- | --- | --- | --- |
| 周一 上午 | 运行采集 + 判定 + 生成周报 | 系统 | `WEEKLY_BRIEF_00N.md`（候选） |
| 周一 下午 | **人工复核**：逐条打开官方链接，标注复核状态与修正 | 运营者 | 周报的 `review_status` 字段 + 修正记录 |
| 周一 傍晚 | **独立对照检索**（见第 4 节），形成本周参考事件集 | 另一位（不使用者）| `reference_events_weekN.json` |
| 周二 | 发送周报 + 反馈表链接 | 运营者 | — |
| 周二–周四 | 用户阅读（≤30 分钟），给出逐条反馈 | 用户 | 反馈表 |
| 周五 | 汇总指标、记录异常与人工工作量 | 运营者 | `metrics_weekN.json` |

**允许**人工复核、人工补充、人工纠错；但必须区分：系统自动发现 / 人工补充发现、系统判断 / 人工修正。
周报的 `field_basis` 与 `review_status` 就是为这个区分而存在的。

## 4. 独立对照：如何发现「系统漏掉的真事件」

目的不是评价系统展示出来的内容，而是**找出它没找到的真实事件**。因此对照必须独立于 MedRadar 的默认 Feed。

**执行者**：一位不参与周报生成的人（可以是运营者的同事），只拿到检索式，不拿到本周周报。

**固定检索式（每周同一套，不允许按结果调整）**：

1. openFDA 召回：`/device/recall.json?search=product_code:"MHX"`（以及 DQA、DSN 等本周轮换的 3 个码），按 `event_date_posted` 排序取本周；
2. openFDA 召回：`/device/recall.json?search=reason_for_recall:(monitor OR alarm OR oximet*)` 取本周；
3. FDA 器械安全通讯页面（人工浏览最近 7 天）；
4. PubMed：`("patient monitor" OR oximetry OR "blood pressure" OR capnography OR telemetry) AND ("intensive care" OR ICU)`，日期限定本周；
5. 两家目标企业官网的新闻/安全通知页（人工浏览）。

**记录格式**（写入 `reference_events_weekN.json`，与 `_evidence/reference_events.json` 同结构）：
`ref_id`、`event_identity`（FDA 事件号，若有）、`official_identifier`、`title`、`public_date`、`source`、`source_url`、`why_reference`、`found_by`。

**时间预算**：每周 60–90 分钟。**这一步不能省**，否则召回率无从计算。

## 5. 指标定义（含分母，含限制）

| 指标 | 公式 | 分母 | 限制 |
| --- | --- | --- | --- |
| 参考事件召回率 | 参考集中被系统识别（任意视图）的事件数 / 参考集事件数 | 本周参考集 | 参考集由一个人用固定检索式构造，是**下界**，不是真理；且「识别」只统计本周窗口载入的事件，早于窗口且窗口内无变化的历史事件不会被计入 |
| 正式周报精确率 | 用户判定为 VALUABLE 或 INVESTIGATE 的条目数 / 被评分的条目数 | 本周正式情报 | 需要用户逐条评分；未评分不计入分母，但必须报告未评分数 |
| 重要事件漏检数 | 参考集中重要（CRITICAL/HIGH 级）但系统未识别的条目数 | 本周参考集 | 「重要」由运营者判定，需附理由 |
| 错误事件数 | 用户判定为 INACCURATE 的条目数 | 本周正式情报 | 必须记录原因 |
| 重复事件数 | 同一事件身份出现在周报多次的次数 | 本周正式情报 | 系统已按事件身份合并，重复应为 0 |
| 事件发现延迟 | `first_observed_at - published_at` 的中位数（天） | 本周新公开事件 | 建库/回填期不可用；只有增量期才有意义 |
| 值得阅读的条数 | 用户 VALUABLE 计数 | — | 个案，不做统计推断 |
| 已知信息条数 | 用户 ALREADY_KNOWN 计数 | — | 同上 |
| 后续行动 | 用户填写（转发/查资料/内部讨论/无） | — | 自由文本，不评分 |
| 时间成本节省 | 用户自评本次阅读 vs 自己检索的时间 | — | 自评，有偏 |
| 继续使用意愿 | 用户 1–5 分 | — | — |
| 采集成功率 | 成功的来源运行数 / 计划运行数 | 本周运行 | 只有真正运行才有意义 |
| 人工复核工作量 | 运营者实际花费分钟数 | 本周 | — |

**明确禁止**：用少于 3 周的数据宣称「统计上有效」；用「用户喜欢」代替「用户采取了行动」。

## 6. 反馈表（逐条 + 整体）

每条正式情报一个判定，取值固定五种（见 `PILOT_FEEDBACK_TEMPLATE.csv`）：

| 判定 | 含义 | 需要填原因 |
| --- | --- | --- |
| `VALUABLE` | 此前不知道，且有用 | 一句为什么有用 |
| `ALREADY_KNOWN` | 我已经知道 | 从哪知道的（可选） |
| `NOT_RELEVANT` | 与我的产品线无关 | 为什么无关 |
| `INACCURATE` | 信息不准确 | **必须**写明哪里不准确 |
| `INVESTIGATE` | 值得进一步调查 | 想调查什么 |

**不能只统计正面反馈**：汇总时必须同时给出五类的计数与原因分布。

## 7. 停止 / 收窄条件（事先登记）

在**至少完成 3 周**之后，按下列顺序判断（不满足上一档才看下一档）：

| 结论 | 条件（全部满足） |
| --- | --- |
| **CONTINUE** | 依从性：≥3/4 周打开并点开 ≥3 条原始证据；价值：≥2 条 VALUABLE；精确率 ≥ 0.50；参考召回 ≥ 0.70；人工复核 ≤ 60 分钟/周 |
| **NARROW FURTHER** | 依从性满足，但精确率 < 0.50 或价值条目 < 2 或召回 < 0.70 → 收窄设备集合或交付频率 |
| **RECONSIDER** | 依从性不满足（≥2 周无人打开），或精确率 < 0.30，或参考召回 < 0.50，或人工复核 > 120 分钟/周 |

**不得因为已经投入开发就选择 CONTINUE。** 三个月后回看，如果结论是 RECONSIDER，本轮的工作仍然有价值（它证明了这个方向不成立）。
