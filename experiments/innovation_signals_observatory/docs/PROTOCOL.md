## 1. 研究问题与操作化

核心问题（MISSION 口径）：
**医疗器械企业公开的技术招聘活动，能否为其新兴研发方向提供可信、可追溯的早期证据？**

| 子问题 | 操作化定义（本轮实际测量的东西） | 数据产物 |
|---|---|---|
| Q1 能否持续获取真实公开技术岗位？ | 每家企业每次采集：岗位数、去重后独立岗位数、字段可获得率（ID/日期/描述/地点）、robots 判定、请求数、失败明细 | `collection_<company>.json` |
| Q2 能否准确识别岗位要求的具体技术能力？ | 规则臂与模型臂的：schema 合规率、**逐字引用可定位率**、引用是否支持标签、弃答是否正确 | `results/2026-11-04/llm/` |
| Q3 能否区分一般招聘与值得调查的方向变化？ | 需要**至少两次时间上分离的快照**才能定义「变化」。本轮只有单次快照 → 只能验证「身份/版本/去重」机制，**不能**给出方向变化 | `medradar/recruitment/identity.py` + 双快照离线测试 |
| Q4 这些变化能否找到独立证据支持？ | 只读关联既有证据库（FDA 监管事件、ClinicalTrials.gov、TEP/论文摘要），逐条给出「关联成功/无关联/时间不兼容」 | `results/2026-11-04/evidence_linking.json` |

**本轮不做的**：不做「招聘 → 未来销量/股价」的预测；不做 lag 检验（D-028/D-029/D-031 已证明
公司级历史序列覆盖不足，本轮的 90 天设计是为将来做时间序列，而不是现在假装已有时间序列）。

## 2. 数据与合法访问原则（不可协商）

1. 只使用**公开、无需认证、robots.txt 允许**的企业招聘页面与其站点自身使用的公开 JSON 端点。
2. **不**绕过验证码、登录、付费墙、反爬或任何访问控制；**不**采集应聘者个人信息、简历、联系方式。
3. 每次采集前先取 `robots.txt` 并在代码中**断言**路径允许（`medradar/recruitment/politeness.py`），
   证据随数据一起保存。robots 未取到 → 拒绝采集，而不是「先采再说」。
4. 频率与体量有上限：同主机 ≥0.8 s 一次请求；单次运行请求数、岗位数均有硬上限，并写入报告。
5. 无法合法稳定获取的企业 → 记 `SOURCE_UNAVAILABLE` / `BLOCKED`，**不虚构岗位，不用第三方爬虫绕路**。

## 3. 观察单元与三类时间的严格分离

**观察单元**：`Company × Technology Track × Observation Time`（本轮首次快照记为 `T0`）。

每条岗位记录必须区分三个时间（与 Live Observatory 的既有语义一致）：

| 字段 | 含义 | 谁写入 | 可否覆盖 |
|---|---|---|---|
| `source_posted_at` | 来源自己声明的发布时间 | 来源 | 可（来源会改） |
| `source_posted_quality` | 该时间的精度/合法性：`SOURCE_DATE` / `RELATIVE_ONLY` / `NONE` | 采集器判定 | 随字段变化 |
| `first_seen_at` | **我们第一次看到该岗位的时刻** | 我们的墙钟 | **永不覆盖** |
| `fetched_at` | 本次采集尝试的时刻 | 我们的墙钟 | 每次覆盖 |
| `source_updated_at` | 来源自称的更新时间（若有） | 来源 | 可 |

**禁止**：用 `first_seen_at` 冒充岗位发布日期；把 `Posted 29 Days Ago` 换算成日期；
把「网站上消失了」解释成「招到人了」；把「重新发布」解释成「新增需求」。

## 4. 三层评价（预先声明的指标）

### 第一层：数据源可行性

对每家企业报告：可访问性、抓到的岗位数、**独立岗位 ID 可用率**、**来源日期可用率**、
**描述可用率**、去重稳定性（两次采集中身份键一致的比例）、采集完整性（是否触到上限而被截断）。

**预先声明的判定**（写在这里，避免事后挑标准）：

* `VERIFIED`：有合法路线；岗位数 ≥20；ID 可用率 ≥0.95；描述可用率 ≥0.90；
  来源日期可用率 ≥0.50（否则只记为「有岗位、无可靠日期」）。
* `EXPLORATORY`：能拿到真实岗位，但上述任一项不达标或样本过小，无法支撑任何时间比较。
* `BLOCKED`：没有合法稳定路线，或 robots 拒绝，或网络/接入不可用。
* `NOT_RUN`：未尝试。

**未观察到岗位 ≠ 企业没有招聘。** 覆盖率的分母未知，本轮只报告「我们能看见多少」，不报告「企业有多少」。

### 第二层：信息抽取可靠性（A 规则 vs B 未微调 Qwen3-4B；C 既有适配器 = NOT_RUN）

指标（与 #19/#20 同口径，便于跨轮比较）：
JSON 合法率、schema 通过率、**逐字引用可定位率**、引用支持率、正确弃答率、
错误弃答率、**负对照误报率**、中位延迟、错误类型计数。

**预先声明**：
* 没有人工金标准 → **不计算 Precision / Recall / F1**，任何「一致率」都只对机器可核查的那部分生效。
* 负对照集合（真实存在的非技术岗位，如 Buyer/Planner、Customer Service、Co-op Non-Tech）
  是**必报指标**，不是可选项：模型在负对照上编造技术方向，比漏抽更严重。
* 模型给出的置信数字**不得**当作校准概率。
* 若 B 臂的 JSON 合法率 < 0.80，则本轮不得基于模型输出做任何汇总统计（只能报失败率）。

### 第三层：证据解释的可核实性

对每个候选信号，产出人类可读材料：原始来源 URL、具体岗位、分类与原文引用、
关联记录（成功/失败都写）、正反证据、研究假设、仍缺失的信息。
**没有关联证据本身是结果**，不允许用模型补齐。

## 5. 信号分级（术语被严格限定，避免「发现」通胀）

| 标记 | 含义 | 允许的表述 |
|---|---|---|
| `OBSERVED_FACT` | 来源明确写出、可逐字定位的事实（如某岗位在某日发布） | 「观察到……」 |
| `CLASSIFIED` | 依据规则/模型得到的分类，附引用与不确定性 | 「按……规则归类为……」 |
| `CANDIDATE_TECHNICAL_HIRING_SIGNAL` | 同一企业、同一技术方向、多个独立岗位 ID 在观察窗内同时出现 | 「值得进一步调查的候选信号」 |
| `HYPOTHESIS` | 研究假设，需独立证据核验 | 「假设……」 |
| `INDEPENDENTLY_SUPPORTED` | 有来源独立的证据（监管/试验/论文/官方公告）指向同一方向 | 「有独立证据支持」 |
| `CONTRADICTED` | 有独立证据与该方向不符 | 「存在反证」 |
| `UNKNOWN` | 该问题现有数据无法回答 | 「目前不可知」 |

**禁止**：把 `CANDIDATE_...` 写成「该企业正在开发 X」；把 `CLASSIFIED` 写成客观事实；
把单次快照的岗位数量写成「趋势」。

## 6. 跨来源关联的判定规则（先声明，后执行）

一个候选方向要被标记为 `INDEPENDENTLY_SUPPORTED`，必须同时满足：

1. **同一企业或可确认子公司**：企业归属来自 `config/universe_v1.json` 的确定性实体键或既有 roster 别名；
   不做模糊匹配。
2. **同一技术方向**：使用既有 `config/tracks_device.json` 的 track/domain 词表，不新造分类。
3. **时间关系合理**：独立证据的时间不早于相应招聘观察超过 24 个月（避免把「十年前的论文」当支持证据）；
   具体窗口写死在代码里并输出。
4. **逐字可定位**：关联用到的每段证据都有可回查的来源标识（监管编号、NCT 号、PMID/DOI）。

不满足任一条 → 记为 `NO_INDEPENDENT_SUPPORT` 或 `CONTRADICTED`，并写明缺哪一条。
**两个事件出现在同一家公司，不构成同一研发项目的证据。**

## 7. 本轮允许/不允许的结论尺度

允许：
* 「在 T0 快照中，企业 X 有 N 个独立岗位 ID 落在 track Y，其中 M 个岗位的原文包含可逐字定位的能力短语。」
* 「该观察不足以支持 track Y 的增长判断，因为只有一次快照。」
* 「模型臂在真实岗位文本上的 schema 合规率为 P，引用可定位率为 Q，负对照误报率为 R。」
* 「五家企业中 k 家存在合法可用的公开采集路线。」

不允许：
* 「企业 X 正在转向技术方向 Y。」（需要时间序列 + 独立证据）
* 「招聘数据显示企业 X 的研发投入增加。」（岗位数 ≠ 投入，且覆盖率未知）
* 「模型能以 X% 准确率识别技术方向。」（没有人工金标准）
* 任何基于 #20 已有数字的「模型能力提升」再叙述。

## 8. 90 天前瞻观察的执行前置条件（写进协议，避免事后补）

只有当以下四条全部成立，才建议启动长期观察：

1. 至少一家企业的采集链路在同一天内重复运行两次，身份键稳定率 ≥0.98，且 `first_seen_at` 未被覆盖；
2. 采集器在 robots 变更或来源改版时会**拒绝或记录结构变化**，而不是静默返回 0 条；
3. 分类器的 `UNCLASSIFIED` 率与负对照误报率已知且有上限；
4. 有明确的失败预算（每次采集的请求/时间上限）与人工复核入口。

否则先修链路，不启动长期观察。长期观察的调度配置样例见 `docs/NINETY_DAY_PLAN.zh-CN.md`，
**本轮不部署任何持续运行的服务**。
