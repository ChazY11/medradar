# MedRadar S-031 研究协议：从公开招聘识别技术能力需求

研究名称：Technical Hiring Capability & R&D Evidence Study  
研究编号：S-031（已检查分支与研究目录，未发现编号占用）  
研究日期：2026-11-05  
标签状态：`AI_PRELIMINARY_LABEL`

## 1. 研究问题与边界

本研究回答一个窄问题：如何从真实公开招聘文本中识别企业正在寻求的技术能力，同时不把销售活动、产品背景和一般岗位招聘误读为新的研发战略。

本研究不回答招聘能否预测产品成功，不估算研发投入，不判断企业是否已进入新市场，也不比较五家公司的创新能力强弱。公开 Careers 页面反映的是采集时可见的在招岗位存量，不是新增招聘流量，更不是企业全部用人需求。

本文件固化实际执行的研究流程。分层规则、固定种子和配额在逐条预标注之前已经写入 `select_sample.py`；本文件不是对外部时间戳预注册的追认。

## 2. 独立性与真值规则

1. 先读原始岗位文本，建立四维预标注，再运行 PR #21 旧规则。
2. PR #21 的旧标签只是比较对象，不是人工金标准。
3. S-031 的 AI 预标注同样不是人工金标准。
4. 差异数量只表示需要审查的分歧，不表示任一方错误率。
5. 没有双人独立人工标注和 adjudication 前，不计算准确率、Precision、Recall 或 F1。
6. 文本缺失时保留 `UNCLASSIFIED` 与 `INSUFFICIENT_EVIDENCE`，不凭 URL 或公司印象补全。
7. 所有输出只允许 `AI_PRELIMINARY_LABEL`；禁止 `HUMAN_GOLD`、`EXPERT_CONFIRMED`、`SCIENTIFICALLY_VALIDATED`。

## 5. 身份、版本与去重口径

- `posting_id` 是不透明源身份 ID。标题 slug 和需求号都不是唯一身份。
- 原 JSONL 行另算 SHA-256，保存为 `raw_record_sha256`；它与岗位内容的 `content_sha256` 不混用。
- 当前 Medtronic 文件经独立流式重算为 994 行、994 个唯一 `posting_id`、0 个同 ID 重复行。
- 994 条保存的 `content_sha256` 均可由当前 `records.content_hash(title, location, description)` 重算一致，但 994 条都缺少 `hash_rule_version` 字段。这个来源缺口不 retroactively 修补。
- 早期 `EVIDENCE_REPORT.zh-CN.md` 记录的是另一口径：994 行中 2 行为同 ID 分页重复，去重后 992。其文件 SHA `165dce8e…f80217` 在当前分支历史中不可取得，因此只能标为“文档记录，源文件未独立复核”。
- 当前 994 唯一 ID 再按保守规则处理 5 个同标题、同地点、同描述簇和 3 个多城市簇，共合并 11 条，得到 983 个分析簇。983 不是已证明的实际空缺人数；多城市发布与同时招多人仍保留歧义。

## 6. 100 条困难分层样本

### 6.1 选样算法

固定种子 `31031`。每个候选岗位的排序键为：

```text
SHA256("31031\0" + company + "\0" + posting_id)
```

每层按该十六进制摘要升序选取。选样只读取标题表层线索、困难产品词和文本可用性，不读取旧规则输出，也不读取 AI 预标注。层内配额不足时，从该公司剩余岗位按同一排序键回补，并在 CSV 标为 `backfill_after_stratum_shortage`。

### 6.2 每家公司目标配额

| 层 | 每家公司目标 |
|---|---:|
| 正文不可用 | 1 |
| 困难产品背景/机器人/AI 等 | 2 |
| 明确研发标题 | 2 |
| 软件算法标题 | 2 |
| 产品工程标题 | 2 |
| 制造标题 | 2 |
| 质量法规标题 | 2 |
| 临床应用标题 | 2 |
| 现场服务标题 | 1 |
| 销售市场标题 | 2 |
| 商业运营标题 | 1 |
| 职能模糊标题 | 1 |

实际得到 100 条，五家公司各 20 条。9 条为配额不足后的确定性回补：

- Medtronic：正文不可用层缺 1。
- GE：无缺口。
- Philips：困难产品背景层缺 1。
- Dräger：困难产品背景层缺 2。
- Mindray：正文不可用层缺 1、困难产品背景层缺 2、质量法规标题层缺 2。

最终分层计数为：困难产品背景 5、明确研发 10、软件算法 10、产品工程 10、制造 10、质量法规 8、临床应用 10、现场服务 5、销售市场 10、商业运营 5、职能模糊 5、正文不可用 3、回补 9。

这是故意增加困难案例的研究样本，不是代表性随机样本。样本内比例不能外推为五家公司岗位结构，也不能用于公司间排名。

### 6.3 每条样本保存的身份信息

`S031_SAMPLE_100.csv` 保存公司、原始岗位 ID、标题、URL、原记录哈希、内容哈希、原始文件哈希、JSONL 行号、选择层、选择原因、数据缺口、采集状态和来源发布日期。`job_id` 与源行号共同支持回查。

## 7. 四维预标注流程

1. 按 CSV 顺序逐条阅读标题和正文。
2. 记录主职能与辅助职能，允许一个岗位同时有工程、项目管理、质量或商业职责。
3. 记录原文明确要求的技术或专业行为能力；没有充分证据时保留空数组。
4. 单独记录产品、业务线、客户环境和内部运营背景。
5. 依据实际活动动词判定研发证据强度，而不是依据产品词的先进性。
6. 保存一段可定位的逐字原文、支持解释、替代解释、缺失信息和人工复核需求。
7. 完成 100 条后，才批量运行 `classify_rules()` 并比较。

预标注由研究 Agent 的语言理解完成，构建脚本只负责写入和校验，不是另一个独立模型复核。本轮没有进行第二轮盲化 AI 标注，因此不存在“AI 间一致即真值”的推断。

## 8. 引文与证据校验

引文匹配规则为 `exact_text_after_unicode_whitespace_normalization`：先做 Unicode NFC，再把连续空白统一为一个空格，词语、数字和标点内容不得改写。97 条有正文的样本均有通过原始描述回查的引文；3 条 `DETAIL_FAILED` 记录没有正文，引文数组为空。

引文只证明原文存在，不自动证明解释正确。每条仍保存替代解释，例如“直接研发职责也可能只是既有产品维护”“熟悉产品可能只用于销售”。

## 9. 旧规则比较方法

对同一 100 条原始标题和描述调用 PR #21 当前函数：

```python
classify_rules({
    "job_title": record["job_title"],
    "job_description": record.get("job_description") or ""
})
```

保存函数类、track、track 状态、规则版本和命中证据。比较时分四种审查候选：错误技术归因、漏掉技术能力、产品—能力混淆、无支持推断。候选只表示值得复核，不自动宣判旧规则或 AI 标签错误。

由于旧规则是单标签、S-031 是主/辅助多标签，函数比较另做宽口径家族映射；该映射只用于定位分歧，不是金标准等价表。

## 10. 可证伪假设

- H1：明确研发岗位的具体技术职责，比销售或市场岗位的产品关键词更适合观察研发能力需求。
- H2：将 Role Function 与 Technical Capability 分开，比单纯按产品 track 关键词分类更可能减少错误归因。
- H3：即使可靠识别研发能力，也未必能证明企业正在进入全新技术方向。

每个假设都必须同时寻找支持案例、反例或限制，并提出未来能否定它的观察。若人工金标准显示销售岗位在控制产品背景后同样提供高价值研发信息，或四维方案并未减少人工确认的错误归因，应否定或收缩 H1/H2。若时间序列与独立项目证据显示可靠能力标签可以稳定预示新方向，H3 的强形式也应被修正。

## 11. 禁止的评价与推断

- 不把描述性分歧当准确率或错误率。
- 不把 `MAPPED` 当直接研发证据。
- 不把 `DIRECT_R&D_EVIDENCE` 当战略转向证据。
- 不把岗位数换算成研发预算、团队规模或项目数量。
- 不把一次快照当趋势，不把来源缺失当企业没有研发。
- 不用本样本比较五家公司的研发强弱。
- 不报告未经人工金标准支持的 Precision、Recall、F1 或准确率。
